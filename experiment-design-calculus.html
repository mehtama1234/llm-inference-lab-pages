experiment design calculus

Turn every inference formula into a controlled experiment.

This page is the bridge from the mathematical writeups to the actual Colab, Unsloth, Hugging Face, TGI, vLLM, TensorRT-LLM, and JetStream runs. It says what variable to change, what to hold fixed, what metric should move, and what claim the result can honestly support.

method

The experiment starts from a predicted movement, not from a command.

A run is meaningful when we can say the mechanism first. If the mechanism is KV reuse, predict lower repeated compute and higher memory use. If the mechanism is quantization, predict lower bytes and possible reconstruction error. If the mechanism is batching, predict higher GPU occupancy and possible queue waiting.

controlled experiment = mechanism formula + one changed variable + constants held fixed + predicted metric direction + measured artifact + allowed claim + locked claim + next stronger gate
Mechanism before metric Do not ask "is it faster?" first. Ask which term in the equation should shrink or grow.
Control before comparison Same model, tokenizer, prompt template, request IDs, host, client, metric definitions, and output limits.
Boundary before conclusion A Colab result, a script result, and a production serving result are different kinds of evidence.
experiment lanes

Each lane should have a predicted mathematical movement.

Prompt and template formula
prefill work grows with prompt tokens. change
plain prompt vs chat template vs RAG/tool-shaped prompt. hold fixed
same text payload, tokenizer, model, and generation cap. measure
token count, prefix reuse opportunity, TTFT risk. claim

KV cache formula
KV bytes scale with layers, tokens, KV heads, head dim, and dtype. change
cache enabled/disabled, prompt length, output length, shared prefix. hold fixed
same model weights, sampling, and request sequence. measure
decode step time, memory growth, admitted tokens, OOM boundary. claim

Quantization formula
w_hat = scale * code; error = w - w_hat. change
bf16/fp16 baseline vs 8-bit/4-bit load path. hold fixed
same prompt set, generation params, and model family. measure
VRAM, load success, latency, output agreement or task score. claim
fit, speed, and quality must be proven separately.
Speculative decode formula
accepted target tokens saved must exceed draft and verify overhead. change
draft model, proposal length, acceptance threshold. hold fixed
same target model and request distribution. measure
acceptance rate, target calls avoided, total latency. claim
speedup depends on acceptance, not on drafting existing.
LoRA / Unsloth SFT formula
Delta W = B A, rank(Delta W) <= r. change
rank, target modules, dataset, steps, learning rate. hold fixed
base model, tokenizer, dataset split, seed where possible. measure
trainable params, VRAM, loss curve, adapter hash, reload output. claim
adapter-artifact proof before quality proof.
GRPO / reward probe formula
group-relative advantage comes from reward differences inside a prompt group. change
reward function and grouped completions. hold fixed
prompt set, base adapter, sampling, and reward parser. measure
reward distribution, invalid reward rate, format adherence. claim
reward contract validity before reasoning improvement.
Colab boundary

Colab is excellent for mechanism and workflow proof, weak for production speed claims.

Colab gives useful GPU access and lets us run Hugging Face and Unsloth notebooks end to end. The weakness is not that Colab is bad. The weakness is that the host, quota, runtime image, and background load are not controlled enough for a durable production runtime conclusion.

strong Colab claimNotebook setup works, GPU is visible, model loads, adapter trains, artifact saves, artifact reloads, and the resulting files are hashable.
medium Colab claimA mechanism moves in the predicted direction under that session: token count, memory fit, acceptance rate, loss trend, or output format rate.
weak Colab claimRuntime A is generally faster than runtime B. This needs the matched host capstone with controlled request replay.
next gatePromote only mature Colab lanes to the NVIDIA Docker host run: same prompts, same model, same output caps, same client, same metrics.
runtime comparison

The capstone runtime experiment should identify the binding constraint.

A fair TGI/vLLM/TensorRT-style comparison is not a scoreboard until it says what constrained the run. The bottleneck may be model weight bandwidth, KV memory, prefill bursts, decode occupancy, queue wait, client streaming overhead, or admission policy.

runtime result interpretation: if TTFT high and prefill queue high -> prefill/admission bottleneck if ITL high with active decode batch -> decode step bottleneck if OOM/rejection before GPU busy -> KV/weight memory bottleneck if throughput high but tail latency bad -> scheduler fairness bottleneck if client gaps dominate -> serving/client protocol bottleneck
vLLM-favoring signalLong/variable prompts, shared prefixes, many active sequences, KV pressure, and admission limited by cache memory.
TGI-favoring signalOperational simplicity, streaming, metrics, tracing, common HF deployment path, and enough throughput under the target SLO.
TensorRT-LLM-favoring signalStable NVIDIA deployment, acceptable engine build complexity, and performance dominated by kernels/engine specialization.
public report template

Every finished run should become a public writeup row or section.

writeup section = 1. question 2. mechanism formula 3. changed variable 4. constants 5. command or notebook path 6. artifact and hash 7. observed metric movement 8. allowed claim 9. locked claim 10. next experiment
good resultThe metric moved as predicted and the artifact proves the run. Promote the claim one level only if the next gate also passes.
surprising resultDo not discard it. Add a first-principles explanation candidate, then run one smaller isolation test.
failed resultKeep the failure if it locks a claim, exposes an environment boundary, or clarifies what Colab cannot prove.
