decision question

For one real workload, which serving path should we trust and why?

The capstone is not "learn every inference trick." The capstone is: choose a serving path for a defined workload and defend that choice from first principles, measured experiments, and explicit non-claims.

serving decision = workload shape + model and tokenizer choice + prompt/output token distribution + prefill/decode accounting + KV memory capacity + runtime comparison evidence + overload policy + adapter boundary + deployment boundary
Workload Prompt lengths, output lengths, streaming requirement, concurrency, timeout budget, and prompt-template stability.
Runtime TGI, vLLM, TensorRT-LLM, or cloud serving path selected by measured bottleneck, not preference.
Boundary Colab proves mechanisms and workflows. The final TGI/vLLM speed claim needs the matched NVIDIA Docker host run.
evidence stack

Every layer of evidence answers a different question.

First-principles math What computation is the model doing? Attention math, KV cache math, and glossary explain the objects.
Model-level probes What do tokenization, cache, quantization, and decoding settings change before a server is added? Hugging Face/Colab runs are mechanism proof, not production speed proof.
Adapter lane Can we create and reload small LoRA/GRPO artifacts? Adapter training math separates workflow proof from quality proof.
Serving pressure Which resource hits first under concurrency: prompt tokens, output tokens, active sequences, batch budget, or KV memory? Serving runtime math maps those pressures to queue and admission formulas.
Matched host proof On the same NVIDIA host, same model, same workload, and same client, how do TGI and vLLM differ? This is the locked evidence gate for a runtime winner.
decision calculus

The runtime choice follows the bottleneck.

Long TTFT Likely pressure: queue wait, prompt length, prefill batching, cold start, or tokenizer/template bloat. Try prompt reduction, prefix cache, chunked prefill, admission limits, and separate long-prompt traffic.
Bad ITL Likely pressure: decode step time, active sequence count, memory bandwidth, KV reads, or scheduler policy. Try decode batching settings, lower active sequence cap, quantization checks, or a runtime with better decode scheduling.
OOM under traffic Likely pressure: KV cache growth, too many active requests, large context, large output cap, or poor allocation. Use KV byte accounting, PagedAttention/vLLM evidence, stricter token caps, lower precision where safe, and admission control.
High average throughput, bad p95 Likely pressure: unfair scheduling, overload, mixed long/short requests, or retry amplification. Use p95, queue wait, timeout, breaker, retry budget, and traffic shaping rather than tokens/sec alone.
Need changed behavior Serving knobs do not change model skill. Adapter training may move behavior. Use LoRA/Unsloth only with a separate quality protocol; do not treat adapter setup as serving proof.
claim template

The final writeup should make one narrow claim and show its proof.

The fair TGI/vLLM comparison is the center of the final serving claim: same workload, same host, same client, same model, same metrics, and the same willingness to report failures.

We tested: model: [id + revision] tokenizer/template: [exact version or hash] workload: [file + SHA + request IDs] host: [GPU inventory + driver + container/runtime] runtimes: [TGI flags] vs [vLLM flags] client: [same client, timeout, concurrency, streaming mode] metrics: TTFT, ITL, completion latency, p95, tokens/sec, queue wait, GPU memory Allowed claim: For this workload on this host, runtime A/B showed [measured difference]. Not claimed: Universal runtime superiority, quality improvement, cloud performance, or adapter benefit unless separately tested.
Mechanism section Explain why the result makes sense using attention, KV, batching, and queue math.
Evidence section Show raw run identity, metrics, logs, workload hash, and pass/fail contracts.
Non-claim section Explicitly list what this run does not prove so the page stays honest.
