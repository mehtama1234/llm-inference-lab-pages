The host return must prove that TGI and vLLM did the same work.

A throughput number by itself is not evidence. The mathematical object we need is a matched comparison: fixed inputs, fixed model, fixed tokenizer and chat template, fixed generation bounds, fixed host, fixed GPU, and runtime logs that explain failures instead of hiding them.

execution path

The exact remaining workflow is host run, local import, fairness gate, final comparison.

on the NVIDIA GPU host: sha256sum -c gpu_host_run_bundle.sha256 tar -xzf gpu_host_run_bundle.tar.gz bash run_complete_gpu_host_campaign.sh back on this repo after copying returns: bash receive_gpu_host_returns.sh python3 simulate_tgi_vllm_fair_comparison_gate.py python3 simulate_tgi_vllm_final_comparison.py python3 verify_tgi_vllm_final_comparison.py

This order matters. Importing first checks the packet shape. The fairness gate then checks whether the two runtime rows are comparable. Only after that should the final comparison page move from locked placeholder to measured claim.

decision rules

The math of the final claim is controlled comparison, not benchmark theater.

Both pass, metadata matchUnlock a metric comparison. Report per-metric winners and the operating region where each result was measured.
One runtime fails setupPublish the failure as a diagnostic result. Do not call the other runtime faster because it was the only one that ran.
Metadata mismatchKeep the final winner locked. Different model, tokenizer, prompts, host, GPU, or generation bounds means it was not the same experiment.
Mixed metricsIf one runtime wins latency and the other wins throughput, the result is conditional. The serving decision follows the workload objective.

Do not publish JSON files, archives, notebooks, credentials, or private scripts to the public Pages repo. The public site should show the interpreted evidence and the static reasoning, not the raw return packet.
