end-to-end synthesis

The lab is about turning model arithmetic into a defended serving decision.

The big picture is one chain: tokens become tensor work, tensor work becomes memory pressure and waiting, runtimes trade those pressures differently, experiments bound the claims, and the capstone chooses a serving path for one real workload.

problem

The practical question is: can we serve useful tokens under a latency and cost boundary?

A model is a function that maps a context to next-token probabilities. A serving system has to run that function repeatedly for many users, while keeping weights, KV cache, activations, queues, and streaming inside real hardware limits. The lab is learning which mathematical object each optimization changes and which claim that change can support.

end-to-end claim = defined workload + model/tokenizer/template + token and KV accounting + runtime and host evidence + quality/adaptation boundary + overload policy + explicit non-claims
What the model does It turns token vectors into logits through attention, MLPs, normalization, and sampling.
What the server does It admits requests, schedules prefill/decode, stores KV, batches work, streams tokens, and rejects overload.
What the writeup does It prevents one run from claiming more than the math and evidence actually prove.
chain of reasoning

Read the project as a chain, not as separate tricks.

1. Tokens math
Prompt text becomes token IDs and embedding vectors. why it matters
Token count controls prefill work, context fit, cache size, and cost.
2. Attention math
softmax(QK^T / sqrt(d))V is a learned weighted read over visible positions. why it matters
The model's core power creates the long-context compute and memory problem.
3. KV cache math
Old K/V tensors are identical under fixed prefix, model, positions, and mask. why it matters
Decode becomes a recomputation-to-memory trade: faster steps, larger persistent state.
4. Runtimes math
Batching, paging, kernels, and quantization change service rate, memory layout, and bytes. why it matters
TGI, vLLM, TensorRT-LLM, and JetStream are different policies over the same constraints.
5. Adaptation math
LoRA restricts the update to Delta W = BA; GRPO uses reward differences inside groups. why it matters
Unsloth/Colab can prove adapter workflow and reward-contract behavior before production serving claims.
why the methods exist

Each method attacks one term in the resource equation.

observed user experience = queue_wait + prefill_time(prompt_tokens) + decode_time(output_tokens, active_batch, KV_state) + streaming_overhead resource wall = weights + KV_cache + activations + runtime_overhead <= GPU_memory
KV cache and paging Reduce repeated compute and memory waste, but they can make memory bandwidth and cache capacity the binding constraint.
Batching and scheduling Raise useful GPU work per step, but can move pain into queue wait, TTFT, or tail ITL.
Quantization and LoRA Change the byte and trainable-parameter budget, but quality must be measured because these are approximation or restriction arguments.
experiment logic

The experiments should climb from mechanism proof to serving proof.

Colab/HF runs strong proof
Token accounting, setup, model load, cache behavior, quantization fit, speculative acceptance, adapter save/reload. locked claim
They do not settle production runtime winners because host and scheduler conditions are not controlled enough.
Unsloth runs strong proof
A notebook can train a LoRA adapter, produce hashable artifacts, reload them, and show a local behavior change. locked claim
Quality, GRPO reasoning improvement, and production serving speed need separate evidence gates.
Host runtime runs strong proof
Same model, tokenizer, prompts, output caps, client, GPU, Docker boundary, and metrics across TGI/vLLM or other runtime paths. locked claim
A win on one workload is not a universal runtime ranking.
meaty finish line

The end state is a public case file, not a pile of benchmark fragments.

The strongest final artifact is a defended serving decision for one workload. It should explain the workload, derive its token/KV pressure, show the experiments, choose the serving path, and state what remains unproven.
