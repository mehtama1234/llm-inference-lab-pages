mechanism layer

Watch inference work move.

The big problem is not one trick. A model must turn text into the next token, keep the past state that future tokens need, and share a limited GPU across requests. These diagrams show the moving parts.

Each section starts with the problem, then shows the method used to solve it.
The numbers come from the Colab L4 run when `gpu_experiment_results.json` is present.
The design contract is in `VISUAL_MECHANISM_TEACHING_PLAN.md`: problem, objects, change, stored state, cost, measured result, and code path.

00 / full loop

The whole job is a repeated next-token loop.

The model does not write the full answer in one step. It receives current tokens, runs the layers, scores possible next tokens, selects one, appends it, and repeats.

Why this mattersEvery later cost is paid inside this loop: arithmetic time, memory reads, KV cache growth, and queue delay.
ProblemProduce an answer when the model can only choose one next token per model step.
ObjectsCurrent token row, model layers, next-token scores, selected token, updated token row.
MotionThe dot marks one model step. It moves from tokens to layers to scores to append, then repeats.
Stored afterThe selected token is added to the sequence. Later sections show the stored key and value rows too.
CostEach loop pays time. Longer text also grows the stored state used by later steps.
ProofThe batch result later shows why one step returning many tokens matters for throughput.
Real HF outputQwen2.5-0.5B on L4: 16 output tokens took 412.9 ms; 512 output tokens took 12,430.1 ms because decode repeated many more times.
01 / text to numbers

Text must become stored rows before math can run.

The tokenizer maps text pieces to integer IDs. Each ID selects one row from the embedding table. That row is the starting vector for the model.

Problem solvedGPUs run number programs. Token IDs are the bridge from text to the model's number tables.
ProblemText cannot be multiplied. It must become integer IDs that select stored number rows.
ObjectsText piece, token ID, embedding table row, vector at a sequence position.
MotionThe moving packet shows lookup: text piece to ID, then ID to one table row.
Stored afterThe model now has a shaped tensor: batch x tokens x hidden size.
CostMore tokens mean more rows to process and less room left in the context limit.
ProofThe local traces print token IDs and embedding output shapes. This section does not need a GPU timing result.
02 / matmul

Matmul packs many multiply-adds into one regular shape.

A layer has learned weights. The current token vectors are multiplied by those weights. Large regular shapes let the GPU keep more compute units busy.

Colab resultLoading measured matmul rows.
ProblemA layer must use stored weights to turn current vectors into new vectors.
ObjectsInput rows, weight columns, one output cell, many multiply-add operations.
MotionThe scan marks repeated work over the weight matrix. The pulsing cells mark many output values being produced.
Stored afterThe output matrix becomes the next set of token vectors for the layer path.
CostTime comes from operation count and from reading the input and weight numbers.
ProofThe Colab run compares FP32, FP16, and BF16 matmul speed for known matrix sizes.
03 / attention

Prefill builds a large score table. Decode reads one row.

Attention scores query rows against key rows. During prefill the prompt has many query rows. During cached decode the new token has one query row and reads stored keys.

Colab resultLoading measured attention rows.
ProblemEach position needs a way to use earlier positions when updating its vector.
ObjectsQuery rows ask. Key rows are scored. Value rows are mixed after scoring.
MotionThe left grid shows many query rows. The right row shows cached decode with one new query row.
Stored afterCached decode keeps earlier key and value rows so only the new row must be added.
CostPrefill creates many score cells. Decode creates one score row but still reads the stored history.
ProofAt 4096 positions, the measured prefill and cached-decode times show the shape change.
Real HF proofQwen2.5-0.5B on L4: first-token time rose from 27.09 ms at 64 prompt tokens to 36.69 ms at 1536 prompt tokens after warmup.
04 / KV cache

The cache saves repeated work by spending GPU memory.

After each token, the model stores key and value rows for every layer. Later decode steps reuse those rows instead of rebuilding them from the whole prompt.

Colab resultLoading KV memory rows.
ProblemLater token steps should not rebuild all earlier key and value rows from scratch.
ObjectsLayer count, K rows, V rows, positions, heads, head size, batch, bytes per number.
MotionThe bars fill as stored positions grow. A longer context means longer stored rows.
Stored afterEvery decoded token adds key and value data for later decode steps.
CostThe speed gain spends GPU memory. More positions or more requests use more KV memory.
ProofThe Colab run shows FP16 KV bytes rising from 512 MB to 4 GB as positions rise.
05 / precision

Number format changes bytes moved and math path used.

FP32 stores each number in 4 bytes. FP16 and BF16 store each number in 2 bytes. That changes memory use and can select faster GPU hardware paths.

Colab resultLoading precision rows.
ProblemThe model must store and move many numbers. The byte size of each number changes memory pressure.
ObjectsStored number, bytes per number, FP32, FP16, BF16, total bytes.
MotionFP32 drops four byte blocks per number. FP16 and BF16 drop two byte blocks per number.
Stored afterThe same count of values occupies less memory when each value uses fewer bytes.
CostLower-byte formats can be faster and smaller, but they carry less numeric detail.
ProofThe measured matmul rows show FP16 and BF16 speed paths on the L4 GPU.
06 / batching

Batching makes one GPU step return more tokens.

Decode for one request adds one token. A server can place several requests into the same step, so the GPU does more useful work before the next scheduling decision.

Colab resultLoading batch rows.
ProblemOne decode request returns one token, which may not give the GPU enough work in one step.
ObjectsWaiting requests, active batch, GPU step, one returned token per active request.
MotionRequest dots enter the same GPU step, then the step emits several output tokens.
Stored afterUnfinished requests keep their KV cache and return for another decode step.
CostBatching can raise tokens per second, but requests may wait and the batch uses more KV memory.
ProofReal HF run on L4: batch 1 reached 39.5 aggregate decode tok/s; batch 32 reached 1225.7 tok/s while each request stayed near 38 tok/s.
07 / fit and pressure

The serving problem is a fit problem under time.

A request needs weights loaded, KV cache space, and enough GPU work capacity to return tokens at the target pace. The server's job is to keep useful work running without running out of memory.

Measured runLoading device memory.
ProblemA request can run only if weights, KV cache, and temporary work fit in GPU memory.
ObjectsWeights, KV cache, temporary work, headroom, context length, batch size.
MotionThe packet crosses choices that change memory fit: number format, cache size, batch size, and limits.
Stored afterWeights stay loaded. KV cache grows while each active request generates tokens.
CostIf the memory bar crosses capacity, the setup fails or must change model, context, batch, or placement.
ProofThe L4 run reports about 22 GB of GPU memory, so every fit estimate must fit inside that fixed budget.
