KV cache math deep dive

KV cache turns repeated computation into a growing memory bill.

This page explains the mathematical reason KV cache works, why it is the center of the memory wall, and why PagedAttention, prefix caching, continuous batching, quantization, and admission limits are different answers to the same cache equation.

core idea

During decode, the new token needs the old keys and values, not the old raw text.

In a transformer layer, each token produces key and value tensors. Once the prompt has been processed, those tensors are fixed for that request. Decode can therefore keep them and reuse them instead of rebuilding them from the whole prefix at every step.

for each layer and head: K_old, V_old = cache for visible previous positions q_new, k_new, v_new = projections for the newest token scores = q_new K_all^T / sqrt(d_head) output = softmax(scores) V_all append k_new, v_new to cache
What is saved Projection work for older positions and the need to feed the full growing prefix every decode step.
What is spent GPU memory to store K and V for every active position, layer, and KV head.
What remains The new query still reads the visible cached positions, so long context still has a decode cost.
byte formula

The cache bill is linear in active tokens, layers, KV width, and bytes per number.

KV bytes per active request = layers * 2 # K and V * active_positions * kv_heads * head_dim * bytes_per_number KV bytes for server = sum_over_active_requests(KV bytes per request) + allocator overhead + fragmentation or reserved-but-unused slots
Layers Each transformer layer has its own attention calculation. More layers means more separate K/V tensors per token position.
Positions Prompt tokens and generated tokens both occupy cache positions. A 4k prompt plus 1k generated tokens is 5k active positions for that request near the end.
KV heads and head dim Full multi-head attention stores K/V for each head. GQA/MQA store fewer K/V heads. This is why model architecture changes serving memory even when parameter count looks similar.
Bytes per number FP16/BF16 use 2 bytes per stored value; lower precision cache formats can use fewer. That lowers capacity pressure only if quality and runtime overhead remain acceptable.
why cache works

KV cache is valid because prior K/V rows are deterministic once computed.

With fixed weights, fixed prompt token IDs, fixed position scheme, and fixed previous tokens, the old K/V tensors do not change when the model asks for the next token. Reusing them gives the same attention inputs for old positions.

without cache at decode step t: run model on x_1 ... x_t to rebuild old K/V and score next token with cache at decode step t: run model on x_t only, read cached K/V for x_1 ... x_(t-1), then append K/V for x_t
Mathematical claim The cache is not an approximation. It stores intermediate values that the model would otherwise recompute.
Systems claim The runtime must preserve exact position order, dtype expectations, attention mask behavior, and request ownership.
memory wall

The cache solves repeated work and creates the serving memory wall.

Long prompt More positions before the first output token. TTFT rises and the cache starts larger.
Long output Each generated token appends one more K/V position per layer. Memory grows through the stream.
More users Cache bills add across active requests. The same loaded model can fit at idle and OOM under traffic.
available KV room = GPU memory - model weights - runtime workspace - activation scratch - safety margin

This is the reason active-sequence limits, max-total-token limits, batch-token limits, prompt limits, and eviction policies are not arbitrary flags. They are guardrails around this subtraction.

PagedAttention

PagedAttention changes allocation, not attention meaning.

Attention needs K/V rows in logical token order. It does not require every request's K/V rows to sit in one contiguous physical memory region. PagedAttention splits K/V storage into fixed-size blocks and uses a table to translate logical block order into physical block locations.

logical position -> logical block + offset block table[request, logical block] -> physical block physical block + offset -> K/V row to read
Why it helps Uneven request lengths waste less memory when allocation happens in reusable blocks. More useful KV rows can fit in the same GPU memory, so the runtime can often admit larger batches.
What it cannot do It does not reduce the mathematical need to read visible K/V rows. If latency is dominated by another bottleneck, paging alone will not prove a speed win.
prefix cache

Prefix caching works only when the prefix is identical at the token level.

Two prompts that look close to a human may not share a cacheable prefix. The tokens, chat template, system prompt, tool block, and prefix boundary must match. When they do, completed K/V blocks for the shared prefix can be reused.

cache hit condition: same model revision + same tokenizer + same token IDs through a block boundary + same position scheme + same attention/cache settings
Good fit Shared system prompts, repeated tool schemas, common RAG header blocks, and stable instruction prefixes.
Bad fit Personalized first tokens, changing timestamps, unstable templates, or different tokenizer behavior.
Claim boundary A prefix-cache hit proves skipped prefill for matching prefixes, not faster unrelated prompts.
serving pressure

Continuous batching is useful only inside the KV capacity envelope.

admit request if: prompt_tokens + max_new_tokens <= max_total_tokens batch_prefill_tokens_after_admission <= max_batch_prefill_tokens active_sequences_after_admission <= max_sequences estimated_KV_bytes_after_admission <= available_KV_room
Batching upside More active requests can share GPU work and amortize loaded weights. This improves throughput when the GPU was underfilled.
Batching downside Each active request owns separate KV rows, so cache memory grows with concurrency. Past the knee, queue wait and OOM risk rise faster than useful throughput.
Why host proof matters Colab can teach the mechanism, but the capacity knee depends on exact GPU memory, runtime implementation, launch flags, model, and workload. That is why the matched TGI/vLLM host run remains the fair speed proof.
source and claim map

KV cache is where papers, docs, and experiments meet.

HF cache docs Hugging Face caching docs explain the repeated matrix-work problem in autoregressive generation. Our model-level cache probes test this as a local generation mechanism.
NVIDIA optimization NVIDIA's inference optimization article frames prefill as parallel work and decode as memory-bound work, then gives the KV memory formula. Our byte accounting and host-bundle work use this as the bridge from math to GPU fit.
PagedAttention The vLLM PagedAttention paper targets the fact that KV cache is large, dynamic, and easy to waste. Our vLLM pressure experiments and pending matched host run test whether allocation and batching improvements matter for our workload.
