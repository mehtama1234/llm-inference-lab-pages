unifying question

The common problem is not "make inference faster." It is repeated constrained optimization.

Every generated token is a small decision made under fixed resources: limited GPU memory, limited memory bandwidth, limited matrix math throughput, and limited time before the user notices waiting. The papers differ because they attack different constraints.

per request objective: minimize user waiting subject to: model_quality(model, prompt, decoding) stays acceptable weights + KV_cache + activations + runtime_overhead fit in GPU memory scheduler keeps useful GPU work high evidence boundary is fixed enough for the claim
Arithmetic layer Attention and decoding decide what computation is needed for a token.
Memory layer KV cache, paging, quantization, and adapters decide what can fit.
Evidence layer Serving claims are true only inside the tested model, hardware, workload, and runtime boundary.

For the explicit bridge from each mechanism to a falsifiable lab run, read the paper mechanism atlas, then the mechanism experiment deep map.

Vaswani et al. 2017

Transformer attention works because it turns sequence dependence into weighted memory reads.

The old bottleneck was not just that recurrent models were slow. The mathematical issue was serial dependence: token state at position t had to be built after earlier state. Self-attention changes the object from a recurrence chain to a matrix of pairwise compatibility scores.

Attention(Q, K, V) = softmax(Q K^T / sqrt(d_k)) V Q K^T gives every query token a score against every visible key token. softmax turns scores into a probability-like weighting. Multiplying by V performs the weighted read.
why scaleIf dot products grow with dimension, softmax saturates. Dividing by sqrt(d_k) keeps score variance closer to stable range, so gradients and probabilities do not collapse too early.
why headsA single weighted average compresses many relations into one distribution. Multiple heads give several learned score spaces, so syntax, position, topic, and copying-like behavior can be represented in parallel.
serving effectPrefill can compute many token-position interactions together. Decode cannot avoid the next-token loop, but it can reuse old K and V rather than recompute them.
failure modeThe score matrix grows with sequence length during prefill. Long context makes attention and KV memory the controlling variables.

Source: Attention Is All You Need.

vLLM / PagedAttention

PagedAttention works because logical token order does not require contiguous physical KV memory.

The KV cache is a growing table of key and value vectors for each active request. A naive allocator treats each request like it needs one contiguous slab sized for its possible future. That wastes memory when requests stop early, grow unevenly, or share prefixes.

KV bytes = layers * tokens * kv_heads * head_dim * 2 * bytes_per_element naive allocation: physical address = request_base + token_position * stride paged allocation: logical token_position -> block_id, offset physical address = block_table[block_id] + offset
why it worksAttention only needs the right K/V vectors for visible positions. It does not care whether adjacent logical positions are adjacent in physical memory.
capacity gainFixed-size blocks let the server allocate near the actual token count instead of reserving worst-case space for every request.
sharing gainIf two requests share a prefix, their logical block tables can point to the same physical prefix blocks until the continuations diverge.
experiment implicationThe right test varies prompt lengths, output lengths, and shared prefixes, then measures admitted tokens, throughput, TTFT, ITL, and OOM boundary.

Source: Efficient Memory Management for Large Language Model Serving with PagedAttention.

HF Transformers and TGI

Continuous batching works because decode steps are small, repeated, and mergeable across requests.

During decode, each active request usually contributes one new token position at a time. If the server waits for a fixed batch to finish, fast requests sit idle behind slow requests. Continuous batching changes scheduling: every decode tick can add newly arrived work and remove completed work.

server is stable when: arrival_rate * average_service_work < available_gpu_service_rate batching helps if: useful_parallel_work_gain > scheduling_overhead + padding_or_cache_overhead
why it worksGPUs like larger matrix operations. Grouping active decode work increases useful parallel work without forcing every request to have the same total length.
why TTFT can risePrefill is large and can block decode if admitted carelessly. More throughput can be bought by making some users wait longer.
why ITL mattersAfter the first token, the user experiences spacing between streamed tokens. A high token/sec average can still feel bad if inter-token latency has a long tail.
experiment implicationReport TTFT, ITL, throughput, batch occupancy, queue depth, and rejection together. One metric alone hides the trade.

Sources: Hugging Face Transformers inference optimization, Hugging Face Text Generation Inference, and Hugging Face continuous batching.

quantization / QLoRA

Quantization works when smaller numbers preserve enough ordering and direction.

A model layer mostly multiplies vectors by weight matrices. Full precision stores each weight with many bits. Quantization replaces a weight with a compact code plus scale information. The mathematical bet is that the function is tolerant to small reconstruction error.

quantized weight: w_hat = scale * code error = w - w_hat layer output error: x W - x W_hat = x (W - W_hat)
why it worksIf reconstruction error is small in directions the activations use, logits stay close enough that likely-token ordering often survives.
why it can failRare large weights, outlier activations, long contexts, and tight probability margins can make small weight errors visible in output quality.
QLoRA twistQLoRA keeps the base model frozen and quantized, then learns LoRA adapters through it. Memory drops because the large base weights are compact and optimizer state is mostly for adapters.
experiment implicationSeparate fit proof from quality proof. "Loaded in memory" does not prove the quantized model preserves behavior on the task.

Source: QLoRA: Efficient Finetuning of Quantized LLMs.

LoRA / Unsloth

LoRA works when the needed behavior change lies in a low-dimensional update space.

Full fine-tuning changes a large matrix W. LoRA freezes W and learns a low-rank update. This is not a trick that guarantees quality. It is a restriction: the update must be expressible through a small number of learned directions.

full update: y = x (W + Delta W) LoRA update: Delta W = B A rank(Delta W) <= r trainable parameters = r * (input_dim + output_dim)
why it worksMany task adaptations do not need independent changes in every parameter direction. Low-rank factors can move behavior along the important directions while leaving the base model intact.
why Unsloth helpsUnsloth is useful to our lab when it turns Colab GPU time into reproducible LoRA artifacts with lower setup friction and lower memory pressure.
what it provesA successful notebook proves setup, training loop execution, adapter save/load, and post-adapter inference for that tiny task.
what it does not proveIt does not automatically prove general reasoning improvement, production serving speed, GGUF quality, or that GRPO reward design is correct.

Sources: LoRA: Low-Rank Adaptation of Large Language Models and Unsloth notebooks.

TGI / TensorRT-LLM / vLLM / JetStream

Runtime systems work by choosing different points in the same resource equation.

Runtime documentation often lists features: paged attention, Flash Attention, tensor parallelism, quantization, KV cache reuse, inflight batching, streaming, tracing. The first-principles view is simpler: every feature changes arithmetic cost, memory footprint, memory movement, scheduling overhead, or observability.

observed latency = queue_wait + prefill_compute_and_memory_time + sum(decode_step_compute_and_memory_time) + streaming_and_client_overhead runtime comparison is valid only if: model + tokenizer + prompt template + workload + host + client + metrics are fixed
TGI style claim Production server features matter when the workload needs streaming, metrics, continuous batching, and safe operational controls.
TensorRT-LLM style claim Kernel and engine specialization matter when the model and hardware path are stable enough to justify build complexity.
vLLM style claim Memory management matters most when KV cache fragmentation, long prompts, many concurrent requests, or shared prefixes limit admission.

Sources: Hugging Face TGI, NVIDIA TensorRT-LLM docs, and vLLM PagedAttention paper.

how to turn papers into experiments

The next experiments should prove mechanisms, not slogans.

matched runtime capstone

TGI vs vLLM on the same GPU host

Hold model, tokenizer, prompt template, request list, output cap, GPU, client, and metric definitions fixed. Then vary runtime. The claim is not "which is better"; it is "which constraint dominated this workload on this host."

Unsloth adapter lane

Colab SFT and GRPO probes

Treat notebook success as adapter-artifact proof. Add held-out prompts and reward-contract audits before making a quality claim. Add separate serving runs before making a latency claim.

quantization lane

fit, speed, and quality separated

Measure memory fit first, then tokens/sec and latency, then output agreement or task score. A lower byte count is a mechanism claim, not yet a quality claim.
