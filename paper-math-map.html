reading frame

Read every paper as a proposed change to this chain.

The model computes next-token probabilities. Serving systems decide how to fit, schedule, and measure that repeated computation. Training systems decide how to modify the function cheaply. The sources differ in surface area, but they all act on one of these objects.

text -> token ids -> embeddings -> attention and MLP layers -> logits -> probabilities -> next token serving wrapper -> admission -> prefill -> decode -> KV storage -> batching -> metrics -> overload control adapter wrapper -> frozen W plus trainable low-rank update -> new behavior claim
Mechanism claim A statement about why the method should change arithmetic, bytes, or waiting.
Experiment claim A statement about what happened under a named model, workload, host, runtime, and run ID.
Boundary claim A statement about what the run does not prove, even if it completed successfully.
source map

Paper-by-paper and source-by-source math lens.

Transformer paper

Attention Is All You Need

objectScaled dot-product attention and multi-head attention: softmax(QK^T / sqrt(d))V.
why it worksEvery token builds a learned query, compares it to visible keys, and uses the resulting weights to mix value vectors.
assumptionSequence relationships can be represented by learned vector comparisons rather than recurrence or convolution alone.
failure modeThe formula explains model computation, but not serving capacity, KV memory pressure, or runtime queue behavior by itself.
experimentAttention math page plus local tensor/attention traces: Q/K/V shapes, mask, softmax, value mix, logits.

vLLM PagedAttention paper

Efficient Memory Management for Large Language Model Serving with PagedAttention

objectKV cache layout: logical token blocks mapped to physical GPU blocks.
why it worksAttention needs ordered K/V rows, not contiguous allocation. A block table preserves order while reducing waste.
assumptionKV memory waste is limiting batch size or throughput for the workload.
failure modeIf compute, network, or client latency dominates, better KV allocation may not move user-visible latency.
experimentvLLM pressure run: active sequences, prompt length, output length, block pressure, prefix reuse.

Hugging Face Transformers optimization

Transformers optimizing inference docs

objectLocal generation call: cache mode, dtype, quantization, compile/static shapes, speculative decode.
why it worksIt reduces repeated K/V computation, lowers bytes, or gives the compiler stable shapes.
assumptionThe chosen model supports the cache or precision mode, and the workload has enough repeated decode work.
failure modeFit can improve without speed improving. Static cache can waste reserved space if max length is poorly chosen.
experimentHF Colab probes: cache strategy, quantization fit, speculative decode, tokenizer/template token counts.

Hugging Face TGI architecture

TGI architecture and launcher arguments

objectRouter, launcher, model server, request queue, token limits, batch limits, streaming path.
why it worksIt turns individual generation into controlled service: admit work, batch work, stream results, expose metrics.
assumptionThe launch limits match the real prompt/output distribution and GPU memory budget.
failure modeBad token limits can reject useful requests or admit too many tokens and create OOM or high p95 latency.
experimentMatched TGI/vLLM host campaign: same workload, same GPU, same client, comparable runtime evidence.

NVIDIA inference optimization

NVIDIA technical blog

objectPrefill/decode split, KV byte bill, batching, attention variants, parallelism, kernel/engine efficiency.
why it worksPrefill is parallel matrix work; decode is sequential and often memory-bound. Optimizations target the limiting phase.
assumptionThe bottleneck has been identified correctly: compute, bandwidth, KV memory, launch overhead, or cross-device communication.
failure modeOptimizing the wrong bottleneck gives a polished system with the same observed p95 or throughput.
experimentHost proof first, then TensorRT-LLM build-payback only if repeated traffic can amortize setup complexity.

Google JetStream on GKE

GKE JetStream tutorial

objectDeployment envelope: project, quota, model storage, accelerator topology, cluster, service endpoint, operational checks.
why it worksIt gives the same inference loop a managed serving environment with explicit infrastructure gates.
assumptionCloud setup and accelerator quota are available, and the model/runtime pair is supported by that path.
failure modeDeployment success does not prove runtime superiority; it proves portability and operational readiness.
experimentJetStream/GKE handoff run after local host proof, with model bucket, cluster, service, and request evidence.

LoRA paper

LoRA: Low-Rank Adaptation of Large Language Models

objectLow-rank adapter update: freeze W and train A B so the layer uses W + A B.
why it worksIf the useful behavior change lies in a low-dimensional subspace, a small rank-r update can move logits enough.
assumptionThe adaptation needed for the task is lower-rank than a fully arbitrary update to every weight matrix.
failure modeLow training loss or successful adapter save does not prove broad quality, safety, or serving speed.
experimentUnsloth SFT lane: train small LoRA adapter, save archive, hash files, reload in a fresh session.

QLoRA paper

QLoRA: Efficient Finetuning of Quantized LLMs

objectFrozen quantized base weights plus trainable LoRA adapters, with gradients flowing into adapter parameters.
why it worksQuantized base weights lower memory while the adapter still supplies trainable directions for behavior change.
assumptionThe low-bit base approximation is good enough for the adapter to learn useful changes through it.
failure modeFitting training into Colab memory is not the same as proving durable quality or production deployment performance.
experimentUnsloth setup/SFT/GRPO workflow proofs plus held-out probes; longer quality runs remain a separate gate.

Unsloth notebooks

Unsloth notebooks

objectAdapter training path: frozen base weights plus low-rank trainable update W + A B.
why it worksIf the desired behavior change lies in a low-dimensional update direction, far fewer parameters can move the output distribution.
assumptionThe dataset, reward, and evaluation target the behavior we actually care about.
failure modeTiny SFT/GRPO runs can prove workflow and artifacts while saying little about general quality.
experimentColab L4 setup, SFT LoRA archive, reload probes, GRPO reward contract, GRPO mini-run, held-out probe.

Production overload controls

Local simulations and post-host follow-up plan

objectArrival rate, service rate, queue length, retry rate, timeout budget, admission limit.
why it worksIf arrival rate is kept below measured service rate, queue wait remains bounded instead of growing indefinitely.
assumptionThe measured capacity knee is real for the deployed workload and traffic shape.
failure modeRetries without backoff can turn a small overload into a larger synthetic arrival rate.
experimentRerun overload simulations with host-measured TGI/vLLM throughput and latency anchors.
study order

The right reading order follows dependency, not popularity.

1. Transformer arithmetic Understand embeddings, dot products, attention, softmax, and one-token decode before touching runtime claims.
2. Memory accounting Derive weight bytes and KV bytes. This makes quantization, batching, context length, and OOM behavior legible.
3. Cache and scheduler Study KV cache, PagedAttention, prefix reuse, and continuous batching as storage and scheduling changes around the same model function.
4. Runtime comparison Compare TGI and vLLM only with the same model, workload, host, GPU, client, and run ID.
5. Adapter lane Study Unsloth as behavior-change math: low-rank updates and reward-shaped optimization, with quality claims kept separate.
6. Cloud and engine choices Only after the base runtime proof, decide whether TensorRT-LLM build payback or JetStream/GKE deployment is worth pursuing.
capstone contract

The final deliverable is a defended serving decision with bounded claims.

The paper map tells us what to learn. The experiment ladder tells us what to prove. The public writeup should eventually read like a case file: one workload, one model, measured token bill, measured KV bill, runtime evidence, overload policy, and clear non-claims.

capstone = workload distribution + tokenizer/template bill + prefill/decode and KV accounting + HF model-level knob probes + Unsloth adapter workflow boundary + matched TGI/vLLM host proof + overload policy tied to measured capacity + public HTML result with sources and non-claims
