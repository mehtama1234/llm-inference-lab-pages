first principle

The server is a control system around the model.

What comes inRequests with different prompt lengths, output limits, deadlines, and users. They do not arrive at the same time.
What must be protectedGPU memory, model weights, KV cache room, decode step time, and the waiting queue.
What must come outTokens streamed soon enough for each user, while the GPU stays busy enough to justify its cost.
first-principles microscope

Prefill and decode are two different jobs inside one request.

A request first reads the prompt so the model has the stored rows it needs. That is prefill. After that, the model produces one new token, stores that token's rows, then repeats. That repeated one-token work is decode. This split explains first-token wait, streaming time, KV memory growth, and why batching matters most after generation has started.

prefillReads the prompt before token 1. Longer prompts usually raise time to first token and create more stored KV rows.
decodeRuns again for each output token. Longer answers keep a request active for more scheduling rounds.
batched decodeOne decode step can return one token for many active requests, so aggregate throughput can rise without shortening every single answer.

first-principles microscope

KV cache is the memory bill for keeping active requests alive.

During generation the model stores two sets of numbers for each token position in each layer: keys and values. Those stored rows let the next decode step read earlier positions without rebuilding the whole prompt. The cost is VRAM. Prompt tokens create the starting KV bill, output tokens append to it, and active requests multiply it.

one token positionStores K and V numbers in every layer. More layers, KV heads, vector width, or bytes per number raise the cost.
one requestKV positions equal prompt tokens already read plus output tokens already generated.
many requestsEach active request holds its own KV rows until it finishes, is cancelled, or is moved by a cache policy.

end-to-end microscope

One request moves through checks, GPU work, memory growth, and cleanup.

The pieces above are not separate topics in production. One request carries a prompt, output cap, stream flag, timeout, and identity. The server admits it, runs prefill, streams decode tokens, watches KV memory, handles caller rules, emits metrics, then frees the work.

before GPUAdmission and client rules decide whether the request should enter active work now.
on GPUPrefill creates first-token wait and starting KV rows; decode repeats one-token steps.
after or during waitTimeouts, cancellation, idempotency, and metrics decide whether work continues, stops, or is counted once.

what each system is for

The names differ, but the moving parts repeat.

TGIHugging Face server for text generation. Its docs call out streaming, continuous batching, tensor parallelism, Flash Attention, and Paged Attention.
TensorRT-LLMNVIDIA stack for optimized inference on NVIDIA GPUs. Its docs organize topics around serving, in-flight batching, paged KV cache, scheduling, quantization, and benchmarking.
JetStreamGoogle serving framework for TPU and GPU paths. Google describes continuous batching, KV cache optimizations, and quantization as core serving features.
vLLMOpen serving engine known for PagedAttention and continuous batching. It is a useful practical baseline when we want to run a server on one Colab GPU.
Common jobTurn a changing pile of requests into GPU work that fits in memory and returns tokens steadily.
Common failureThe server admits too much work, wastes memory, blocks decode with long prompt work, or hides the real problem behind one average latency number.

Sliding-window KV caps memory by keeping only recent token positions in selected layers.

A full-context server keeps KV rows for every token in the conversation. That lets later tokens read the whole history, but memory grows with every prompt and generated token. A sliding-window policy keeps only a fixed number of recent token positions in windowed layers.

full contextEvery layer stores every earlier token position. Long chats grow until they hit the KV budget.
sliding windowWindowed layers keep the newest token positions and drop older KV rows from those layers.
hybrid layersSome layers keep full history while other layers use a window, trading memory for long-context reach.

CPU offload moves KV blocks between GPU memory and CPU memory.

CPU offload does not make the KV cache disappear. It changes where colder KV blocks live. Decode can copy a needed block back to GPU, copy a colder GPU block out to CPU, or discard CPU copies and recompute when transfer pressure gets too high.

copy inBring an older CPU block back when decode needs those token positions.
soft resetDrop CPU copies and recompute some KV when transfer work is worse than rebuilding.

Replicas and tensor parallelism spend extra GPUs for different reasons.

A replica is a full copy of a model and helps with more independent requests. Tensor parallelism splits one model across GPUs and helps a larger model fit, but each generated token now crosses a link.

replicasCopy the whole model on each GPU. Capacity grows because more requests can run independently.
tensor parallelSplit one model across GPUs. Fixed weight memory per GPU drops, but GPUs must exchange activations.
combinedLarge models under high traffic may need both shards and copies, which raises GPU count fast.

completed shard-flow simulation

Tensor parallelism splits one layer's matrix work across GPU ranks.

A tensor-parallel rank owns only part of a layer's weight matrix. The same input activation reaches each rank, each rank computes a partial output, then the ranks exchange and assemble those partial outputs before the next layer can run.

weight shardEach rank stores a slice of the layer weights, lowering fixed memory per GPU.
partial outputEach rank computes only its slice of the output numbers for the current token step.
exchangeThe next layer needs the assembled activation, so ranks must communicate every generated step.
