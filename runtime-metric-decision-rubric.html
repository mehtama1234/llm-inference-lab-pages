runtime metric decision rubric

The host result should choose by bottleneck, not by a single scoreboard number.

This rubric defines how the future TGI/vLLM host metrics should be interpreted. It keeps the final decision mathematical: first identify the bottleneck, then choose the runtime or policy that moves that bottleneck under the same workload boundary.

decision rule

The winning runtime is the one that improves the binding term without breaking the boundary.

A runtime can win only for a named workload boundary. If the workload, model, tokenizer, host, client, request file, or generation bounds changed, the comparison is not a comparison. If both systems pass the user-facing goal, the simpler operational choice may be the right answer even if a micro-metric differs.

metric interpretation

Each metric points to a different part of the inference system.

TTFT means
Time until the first streamed token. math
Queue wait plus tokenization/client overhead plus prefill service time. decision
If p95 TTFT fails, prefer the runtime or policy that handles long prompts and prefill contention better.
ITL means
Inter-token latency during decode. math
Per-step decode time shaped by active sequences, memory reads, scheduler cadence, and streaming flush. decision
If ITL fails, prefer the runtime with steadier decode cadence under the same active-load range.
Throughput means
Completed or emitted tokens per second. math
Useful work rate after batching, queueing, and failed requests are accounted for. decision
Throughput wins only if tail latency and errors stay acceptable.
p95 latency means
The slow request boundary, not the average path. math
Tail queue wait, long prompt shape, mixed request lengths, retries, and overload. decision
If p95 is bad while averages look good, pick the system with better overload behavior or admission control.
Errors and rejections means
Requests that failed, timed out, OOMed, or were refused. math
The service capacity constraint was violated or the runtime setup was unstable. decision
A faster runtime with materially worse failure behavior does not win by default.
GPU memory means
Weights, KV cache, allocator overhead, and runtime buffers under active traffic. math
weight_bytes + KV_bytes(active_tokens) + overhead <= VRAM decision
If memory is binding, runtime KV policy, quantization, token caps, and admission control matter more than peak token rate.
decision outcomes

The result should map to one of a few bounded conclusions.

Pick TGI allowed when
TGI passes the workload SLO with comparable or better tail behavior and simpler operation. write
"For this workload and host, TGI met the target with the lower operational burden." do not write
"TGI is generally faster than vLLM."
Pick vLLM allowed when
vLLM improves the binding latency, throughput, memory, or overload term under the same workload. write
"For this workload and host, vLLM moved the bottleneck that mattered." do not write
"vLLM wins every serving case."
Pick neither yet allowed when
Both fail the SLO, both are unstable, or the measured difference is not decision-relevant. write
"The proof returned, but the current setup does not justify a production winner." next
Tune workload, model, concurrency, or host setup and rerun.
Keep locked required when
Archive missing, metadata mismatched, one runtime missing, verifier failed, or fair gate failed. write
Diagnostic evidence only. next
Follow post-host-publication-protocol.html.
no-winner cases

"No winner" is a valid technical result when the evidence does not support a decision.

A rigorous capstone is allowed to end with no winner if the measurement says no defensible production choice can be made yet. That is better than over-reading a noisy or mismatched benchmark.
