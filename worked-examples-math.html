attention example

Dot products become attention weights.

Suppose one query compares against three keys. Use a small head width so the scale is easy: d_head = 4, so sqrt(d_head) = 2.

raw dot scores: [4, 2, 0] scaled scores: [4/2, 2/2, 0/2] = [2, 1, 0] softmax denominator: exp(2) + exp(1) + exp(0) = 7.39 + 2.72 + 1 = 11.11 attention weights: [0.67, 0.24, 0.09]
Largest dot product The first prior token aligns best with the query. Softmax gives it about 67 percent of the read weight. The output vector is mostly that value vector, but still mixes the others.
Why scaling matters Without divide-by-2, scores would be [4, 2, 0]. Softmax would become about [0.87, 0.12, 0.02]. The read becomes much sharper, which can make training and generation less stable.
KV bytes example

One active request can have a predictable cache bill.

Use a small model-shaped example: 24 layers, 2 K/V tensors, 2,048 active positions, 8 KV heads, 128 head dimension, and 2 bytes per number.

KV bytes = 24 * 2 * 2048 * 8 * 128 * 2 = 201,326,592 bytes = about 192 MiB for one active request
10 active requests 10 * 192 MiB = about 1.9 GiB of KV cache. This is separate from model weights and runtime workspace. The loaded model can fit while traffic still exhausts memory.
Double context 4,096 positions doubles the cache to about 384 MiB per request. KV memory is linear in active positions. This is why prompt and output caps are capacity controls.
batching example

Batching helps until KV memory or queue wait becomes the limiter.

available KV room: 8 GiB estimated KV per active request: 192 MiB maximum active requests by KV alone: floor(8192 / 192) = 42 if runtime cap is max_active_sequences = 32: admission cap is 32, not 42
Capacity is min of gates Memory says up to 42 requests. Runtime sequence cap says 32 requests. The true safe cap is the smaller gate.
Why not max it out At 32 active requests, throughput may rise. But TTFT and p95 can worsen if queued prompts wait too long. Capacity planning needs latency, not only tokens/sec.
queue example

Overload is arithmetic before it is an incident.

server sustainable service rate: mu = 20 requests/sec incoming traffic: lambda = 24 requests/sec excess: lambda - mu = 4 requests/sec after 60 seconds: rough backlog growth = 4 * 60 = 240 requests
What users see Queue wait grows even if every individual model step still works. p95 latency worsens first, then timeouts and retries appear. More retries can increase effective arrival rate.
What control does Admission and rate limits reduce lambda. Batching and runtime tuning can raise mu. Stable service needs lambda below measured mu for the workload.
LoRA example

Low rank can cut trainable parameters by orders of magnitude.

Suppose a projection matrix has d_in = 4096 and d_out = 4096. A full update trains every matrix entry. A rank-8 LoRA update trains two thin matrices.

full update params: 4096 * 4096 = 16,777,216 LoRA rank 8 params: 8 * (4096 + 4096) = 65,536 ratio: 16,777,216 / 65,536 = 256x fewer trainable values
Why it fits Optimizer state and gradients track far fewer trainable values. This is why notebook adapter training can fit where full fine-tuning cannot. It is a memory and training-workflow win.
What it does not prove Small adapter files do not prove quality. Quality needs held-out evaluation and baseline comparison. Serving speed still needs a separate runtime test.
speculative decoding example

Speculation pays only when accepted tokens beat draft overhead.

baseline target decode: 4 target steps produce 4 tokens speculative case: draft proposes 4 tokens target verifies them in 1 step accepted prefix = 3 tokens target correction produces 1 more token effective target work: about 2 target steps for 4 output tokens, plus draft overhead
Good case Accepted tokens per verification step is high. The expensive target model runs fewer sequential steps. Latency can improve if draft overhead is small.
Bad case Only 1 of 4 draft tokens is accepted. The target still has to do most decode work. The draft model becomes extra work rather than saved work.
