A runtime comparison is a paired measurement problem.

A fair comparison is not "TGI number versus vLLM number." It is two vectors of measurements indexed by the same requests. If the request set, model, client, host, or clocks differ, the subtraction mixes runtime policy with unrelated variables.

for each request i: delta_metric_i = metric_TGI_i - metric_vLLM_i allowed only when: same request_id_i same model and tokenizer same workload SHA-256 same client SHA-256 same host identity same GPU inventory same GPU_HOST_RUN_ID same timing fields and token fields
Workload equalityThe prompt distribution fixes prefill work. The output caps fix how much decode work is requested.
Client equalityThe same streaming client keeps TTFT, completion latency, token counting, and error handling comparable.
Host equalityThe same GPU and host boundary keep memory bandwidth, kernel stack, network path, and thermal conditions from becoming hidden variables.
Metadata equalityRuntime versions, launch flags, CUDA/PyTorch state, host identity, and proof limits must travel with the numbers.

The final table will compare six clocks, each answering a different question.

Lower latency metrics win when the value is smaller. Throughput metrics win when the value is larger. A runtime can win TTFT and lose full completion, because prefill scheduling and decode throughput are different pieces of the token loop.
