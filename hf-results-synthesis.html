hugging face result synthesis

The Hugging Face runs show that inference speed is several different equations, not one knob.

These Colab L4 results use Transformers around Qwen2.5-0.5B-Instruct. The point is not that this small model is the final system. The point is to isolate which mathematical term moved: prompt length, KV reuse, batch width, weight bytes, or target-model forward calls.

first-principles spine

Transformers generation is prefill once, then cached decode many times.

A prompt of length P first creates hidden states and KV rows for all prompt positions. Then each new token adds one more position and reuses the stored keys and values. Most tuning knobs are ways to reduce one of three costs: rows read, bytes stored, or forward passes executed.

request cost = prefill(P) + sum over output tokens decode_step(P + t, cache_policy) + queue_wait(batch_policy, active_requests) + memory_pressure(weights_bytes + KV_bytes + runtime_overhead)

prompt and prefill

Prompt formatting spends tokens before the model can produce token one.

A chat template, tool schema, or RAG chunk is not metadata outside the model. It becomes token IDs. More input tokens mean more prefill work, more KV rows, and less remaining context room.

KV cache policy

Cache policy changes the shape of decode work, but support and overhead decide the measured result.

The mathematical promise of KV cache is simple: avoid rebuilding keys and values for previous positions. The implementation detail is less simple: dynamic, static, offloaded, and quantized caches have different allocation and transfer behavior.

with cache: decode input rows at step t ~= 1 newest token + stored KV reads without useful cache: decode input rows can grow with P + t measured speed depends on: saved compute - allocation overhead - transfer overhead - backend limits

batch width

Batching raises total tokens per second by making each decode step serve more active requests.

In cached decode, one step can return one next token per active sequence. If the step time stays roughly flat while batch grows, aggregate throughput rises. The tradeoff is that KV slots and memory grow with active requests.

aggregate decode tokens/sec ~= batch_size / mean_step_seconds KV token slots after generation = batch_size * (prompt_tokens + output_tokens)

weight precision

Quantization is a memory-fit lever before it is a speed claim.

Reducing weight bytes can make a model load and leave more room for KV cache. That does not mean the quantized path is faster. Kernel support, dequantization, model size, and generation shape decide speed.

assisted generation

Speculative decoding works only when saved target work beats assistant overhead.

The draft model proposes tokens. The target model verifies a block. If enough proposed tokens are accepted, the target runs fewer forward calls. But the assistant also runs, so forward-call reduction is not identical to wall-clock speedup.

speedup condition: target_time_saved_by_fewer_forward_calls > assistant_draft_time + verification_overhead + batching/shape overhead

bounded conclusion

What these runs let us say now.

Allowed claim For this Colab L4 setup, Transformers generation exposes distinct mechanisms: prompt tokens affect prefill, cache policy affects decode shape, batch width affects aggregate throughput, precision affects fit, and assisted generation depends on accepted draft work.
