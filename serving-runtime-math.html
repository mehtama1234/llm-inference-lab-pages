serving runtime math

A serving runtime is a queueing system wrapped around the token loop.

This page connects the transformer math to TGI, vLLM, runtime flags, batching, streaming, overload control, and the final host proof. The core question is simple: which requests enter, which token work runs together, how much KV memory is reserved, and how long users wait?

core frame

The runtime does not change the model function. It controls when and how often that function is called.

A model call estimates the next-token distribution. A serving runtime manages many such calls under finite GPU memory, finite bandwidth, finite compute, and impatient clients. That is why serving math is queueing plus cache accounting plus repeated decode scheduling.

request -> validate tokens -> admit or reject -> queue queue -> prefill batch -> first token active set -> repeated decode batches -> stream tokens finish -> free KV cache -> update metrics
Request shape Prompt tokens, max output tokens, sampling options, and stream mode define the work contract.
Runtime shape Batch limits, sequence limits, KV allocator policy, and scheduler policy define what can run together.
Evidence shape A runtime claim is only fair when model, workload, host, GPU, client, and run ID match.
queueing

If arrival rate exceeds service rate, waiting grows.

This is the first production fact. No runtime flag can make unlimited traffic fit a finite server. If requests arrive faster than the server can complete useful token work, queued work accumulates.

lambda = arrival rate mu = sustainable service rate stable only if lambda < mu over the measured window if lambda >= mu, queue_wait and p95 latency grow
Why average is weak Average latency can look acceptable while a tail of users waits behind long prompts or long outputs. p95 and p99 expose whether the queue is staying bounded for most users.
Why retries matter A failed or timed-out request can become a second arrival if the client retries immediately. Without backoff and retry budgets, overload creates more overload.
admission control

Admission flags are mathematical gates around token count and KV memory.

request can enter only if: input_tokens <= max_input_tokens input_tokens + requested_output_tokens <= max_total_tokens active_sequences + 1 <= max_active_sequences batch_prefill_tokens + input_tokens <= max_batch_prefill_tokens estimated_KV_after_admission <= available_KV_room
Reject early Rejecting or trimming before prefill avoids wasting GPU work on a request that cannot finish safely.
Reserve honestly Output-token caps are part of memory planning because future generated tokens append future KV rows.
False safety Only checking prompt length can still admit too much total cache growth during decode.
batching

Batching trades lower per-token overhead for higher shared-memory pressure.

A GPU likes larger matrix shapes. Batching gives the runtime more token work per scheduling step. During decode, continuous batching keeps a changing active set: finished requests leave, waiting requests enter, and each active request usually advances by one generated token per decode round.

decode round work = one query token per active sequence + read cached K/V for each active sequence + append one K/V row per active sequence that continues
Throughput win Loaded weights are shared across requests, and larger shapes can use the GPU better. This matters when the server is underfilled.
Latency risk Admitting too much work can delay first tokens and increase inter-token gaps. This matters when user-visible streaming latency is the product requirement.
metrics

Latency metrics are measurements of different parts of the chain.

TTFT = queue_wait + validation/tokenization + prefill_wait + first_decode_gap ITL = time between streamed output tokens during decode completion_latency = TTFT + remaining_decode_time p95 = latency below which 95 percent of observed requests completed
TTFT Mostly exposes queueing and prompt prefill pressure. Long prompts, cold starts, and overloaded prefill batches show up here.
ITL Exposes decode scheduler pressure and per-token runtime cost. KV reads, active sequence count, batch policy, and memory bandwidth show up here.
Tokens/sec Useful for capacity planning, but incomplete alone. A system can have high aggregate token rate while some users have bad p95 latency.
runtime flags

TGI and vLLM expose different surfaces over the same constraints.

TGI documents the serving split into router, launcher, and model server. The router receives requests, queues them, forms batches, and sends work to the model server. The important flags are not just configuration names; they are limits on the equations above.

TGI router TGI architecture docs describe router/webserver, launcher, and model server roles. The router is where request buffering, batching, queues, schedulers, and block allocators become operational behavior.
TGI limits TGI launcher arguments include max concurrent requests, max input tokens, max total tokens, max batch prefill tokens, max batch total tokens, and max waiting tokens. Each one bounds a different source of work, memory, or waiting.
vLLM side The vLLM/PagedAttention result is centered on efficient KV block allocation and high-throughput serving under dynamic sequence lengths. Its advantage must still be measured under the same workload and host rather than inferred from mechanism alone.

Colab runs taught mechanisms: cache, quantization, speculative decode, vLLM pressure, Unsloth adapters. The final runtime claim needs a stricter standard because runtime behavior depends on host details.
