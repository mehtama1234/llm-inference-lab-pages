source-backed scale concepts

The real serving problems behind LLM inference.

This page turns the source notes into diagrams. Each section explains the practical issue, why it happens, the method used, the tradeoff, and what to measure.

big picture

Training, inference, and serving are different jobs.

trainingChange model weights by learning from many full text sequences.
inferenceUse fixed weights to answer one request.
servingAnswer many requests quickly while staying inside fixed GPU memory.
01 / first-token delay

Long prompts delay the first output token.

Before the model can write, it must read the prompt and create state for those prompt positions.

sourcesHF optimization, TGI launcher flags
practical issueUser sends a long prompt and waits before streaming starts.
methodReduce prompt tokens, cache repeated prefixes, chunk long prefill, route long prompts separately.
tradeoffLess context can remove useful information; chunking helps fairness but adds scheduler work.
measurePrompt tokens, time to first token, prefill tokens/sec, queue wait.
real HF runQwen2.5-0.5B on L4: 64 tokens gave 27.09 ms TTFT; 1536 tokens gave 36.69 ms after warmup.
02 / slow streaming

Long answers pay decode cost again and again.

After prefill, the model writes one token, appends it, then repeats.

sourcesHF optimization, NVIDIA inference optimization
practical issueThe first word appears, but the answer streams slowly.
methodBatch decode, reduce output limit, use faster runtime, use speculative decoding when it fits.
tradeoffShort output limits can cut off useful answers. Speculation adds another model and acceptance checks.
measureInter-token latency, decode step time, tokens/sec, output length.
real HF runQwen2.5-0.5B on L4: 16 output tokens took 412.9 ms; 512 took 12,430.1 ms, while decode stayed near 24-26 ms/token.
03 / KV memory wall

The model can fit, but active requests can still run out of memory.

Every active request stores key and value rows for its past tokens.

sourcesNVIDIA, HF KV cache
practical issueWeights load, then traffic causes out-of-memory failures.
methodReduce context or batch, lower cache bytes, page or offload KV cache.
tradeoffSmaller context or batch can reduce quality or throughput. Offload adds transfer time.
measureKV bytes, active tokens, memory left, max tokens before OOM.
04 / paged KV

KV cache blocks reduce memory waste.

Requests grow at different lengths. Fixed large reservations leave unused space.

sourcesPagedAttention paper, vLLM blog
practical issueMemory is reserved but not all reserved slots hold useful token state.
methodSplit KV into fixed blocks and map logical request order to physical GPU blocks.
tradeoffBlock lookup adds implementation work, but more GPU memory stores useful KV rows.
measureAllocated blocks, used slots, wasted slots, active requests, throughput.
05 / continuous batching

New requests can join between decode steps.

Static batches waste slots when some requests finish early.

sourcesTGI overview, Google JetStream tutorial
practical issueSome users wait while the GPU could still process useful work.
methodLet scheduler insert new requests into open active slots between decode steps.
tradeoffHigher throughput can add queue wait. Scheduler must protect memory fit and fairness.
measureActive batch size, waiting requests, tokens per step, TTFT, ITL.
real HF runQwen2.5-0.5B on L4: batch 1 reached 39.5 aggregate decode tok/s; batch 32 reached 1225.7 tok/s while each request still streamed near 38 tok/s.
06 / prefill and decode compete

A huge prompt can disturb active streaming.

Prefill and decode have different work shapes but share the same worker unless the system separates or schedules them carefully.

sourcesTGI launcher flags, TGI architecture
practical issueShort chats pause because another request sent a large prompt.
methodLimit prefill batch tokens, chunk prefill, route long prompts separately.
tradeoffChunking improves shared progress but can delay the long prompt's first token.
measureTTFT, ITL, prefill tokens per batch, decode tokens per batch.
07 / serving architecture

Production serving is more than `model.generate()`.

The system needs request intake, queueing, scheduling, model execution, streaming, limits, and metrics.

sourcesTGI architecture, TGI overview
practical issueOne script cannot manage many request shapes, streaming, memory limits, and metrics.
methodUse router, queue, scheduler, model worker, streaming path, and metrics.
tradeoffThe system gives control but adds knobs that must be measured and tuned.
measureQueue depth, batch size, TTFT, ITL, memory pressure, errors.
08 / production knobs

Serving settings are gates around limited hardware.

The system must choose run, wait, or reject before a request can harm memory or latency.

sourcesTGI launcher flags
practical issueLoose settings cause OOM and latency spikes; strict settings reject or shorten work.
methodSet max input tokens, max total tokens, batch token limits, waiting limits, memory target.
tradeoffProtecting the service limits what some requests can do.
measureRejected requests, p95 TTFT, p95 ITL, OOM count, memory use.
09 / speculative decoding

A small model can draft tokens for the large model to check.

The large model usually writes one token per step. Drafting can let one large-model pass accept several tokens.

sourcesHF optimization
practical issueLong decode streams require many large-model steps.
methodAssistant model proposes several tokens; large model verifies them together.
tradeoffNeeds a good assistant model. Rejected tokens reduce the gain.
measureProposed tokens, accepted tokens, rejected tokens, saved large-model steps.
10 / quantization

Lower-byte number formats help memory fit.

The same count of stored values uses different memory depending on bytes per value.

sourcesTGI overview, NVIDIA
practical issueWeights and KV cache use too much memory or move too many bytes.
methodUse FP16/BF16, int8/int4 weights, or lower-byte KV cache where supported.
tradeoffLower-byte values can affect quality or require specific hardware/runtime support.
measureWeight memory, KV memory, tokens/sec, task quality, numerical failures.
