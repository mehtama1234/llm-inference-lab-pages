common spine

Every method moves one term in the same constrained objective.

The user experiences one thing: time until useful tokens arrive. The system pays for several things at once: weight reads, attention over prior tokens, KV storage, scheduler decisions, network/client waits, and any adapter or reward-induced behavior change. The useful question is not "which tool is best?" It is "which term is binding for this workload?"

serving objective for one workload: minimize P50/P95 waiting and error probability subject to: y_t ~ model(next token | prompt, y_

model math

Transformer and attention papers define the cost we keep trying to rearrange.

Transformer attention

Source: Attention Is All You Need.
Q = X W_Q K = X W_K V = X W_V attention(X) = softmax(Q K^T / sqrt(d_head)) V
object changedA token is no longer processed only by local recurrence. It can form weighted mixtures of all visible prior token vectors.
why it worksThe dot product is a similarity score. Softmax turns scores into a probability-like weighting, so the model can route information by content.
cost createdPrefill scores all prompt-token pairs. Decode scores one new query against every cached key. Context length therefore becomes a direct runtime and memory variable.
lab proofToken counts, prompt shape, KV bytes, and latency must be measured together. A prompt change is a systems change.

FlashAttention-style kernels

Source: FlashAttention.
same mathematical output: softmax(Q K^T / sqrt(d)) V different execution: tile Q, K, V keep partial softmax statistics on chip avoid materializing the full attention matrix in slow memory
object changedThe formula is not changed. The memory traffic pattern is changed.
why it worksSoftmax can be accumulated block by block if the running max and normalizer are tracked exactly enough.
failure boundaryIf attention is not the bottleneck, a better attention kernel may not move end-to-end latency.
lab proofCompare prefill-heavy and decode-heavy workloads separately. Kernel speed is not the same claim as server speed.

Speculative decoding

Sources: speculative sampling and Hugging Face generation references.
draft proposes k tokens: z_1...z_k ~ q(.) target verifies: p(z_i | context, accepted_prefix) speedup needs: accepted_tokens_per_target_call > 1 draft_cost + verify_cost < repeated_target_decode_cost
object changedThe target model still defines the distribution. A cheaper draft model proposes candidate steps.
why it worksWhen the draft often agrees with the target, one target pass can validate multiple tokens.
failure boundaryLow acceptance, expensive draft work, or memory pressure can erase the gain.
lab proofOur HF speculative runs can prove target-call reduction, not a universal latency win.
memory math

PagedAttention, quantization, and prefix caching all attack memory pressure from different angles.

vLLM PagedAttention

Source: Efficient Memory Management for Large Language Model Serving with PagedAttention.
KV_bytes = layers * tokens * kv_heads * head_dim * 2 * bytes_per_element logical token block -> physical GPU block admission improves when wasted_reserved_KV drops
object changedThe KV cache allocation. Logical sequence order is separated from contiguous physical memory.
why it worksServing has many sequences with uneven lengths. Block tables reduce fragmentation and make admission closer to actual active-token demand.
failure boundaryIf compute or client timing dominates, lower KV waste may not improve user-visible latency.
lab proofvLLM pressure probes should vary active slots, prompt length, output length, and prefix reuse.

Quantization and QLoRA

Source: QLoRA plus Hugging Face bitsandbytes paths.
weight_memory ~= parameter_count * bits_per_weight / 8 quantized inference helps if: memory_saved reduces paging/OOM/bandwidth pressure and dequantization overhead does not dominate
object changedThe representation of weights, not the abstract matrix multiply the model wants to compute.
why it worksWeights often tolerate lower precision because learned representations are redundant enough for small rounding errors.
failure boundaryQuantization can hurt quality, add dequantization cost, or fail to help if KV memory is the binding term.
lab proofHF quantization fit proves memory feasibility and load behavior; quality and serving speed need separate probes.

Prefix caching

Sources: vLLM prefix caching docs and local prefix-cache probes.
if prompt = shared_prefix + request_suffix: prefill(shared_prefix) can be reused savings ~= repeated_prefix_tokens * prefill_cost_per_token minus lookup/hash/cache overhead
object changedThe cache key for repeated prefix KV, not the model distribution.
why it worksIdentical prefix tokens produce the same cached keys and values for a fixed model state and template.
failure boundaryTemplate drift, low prefix reuse, or short prompts can make cache overhead larger than savings.
lab proofRun repeated-prefix and unique-prefix traffic side by side. Tokenization must be frozen.
serving math

TGI, vLLM, TensorRT-LLM, and JetStream are policies over the same queue and memory equations.

TGI and continuous batching

Sources: Hugging Face TGI and continuous batching references.
request latency = queue_wait + prefill_time(prompt_tokens) + decode_steps * per_step_time(active_batch) continuous batching tries to keep: active_GPU_work / wall_time high
object changedThe server schedule around prefill, decode, streaming, admission, and metrics.
why it worksDecode steps are small and repeated. Serving many active requests together amortizes GPU work and reduces idle gaps.
failure boundaryBatching can improve throughput while hurting tail latency if queueing grows faster than service rate.
lab proofThe matched host campaign must capture TTFT, output latency, token rate, errors, and admission behavior.

TensorRT-LLM and engine optimization

Sources: NVIDIA TensorRT-LLM docs and runbook references.
speedup source = kernel fusion + lower precision + static engine planning + parallel execution valid only inside: supported model architecture + built engine shape + hardware target
object changedThe compiled execution plan for the same model graph.
why it worksKnown shapes and fused kernels reduce launch overhead, memory traffic, and wasted generic framework work.
failure boundaryEngine build time, unsupported shapes, unsupported ops, or small workloads can dominate.
lab proofTensorRT belongs after the TGI/vLLM host proof because it needs a measured baseline and a compatible GPU host.

JetStream and cloud serving

Sources: Google serving notebooks and GKE/JetStream handoff references.
cloud serving objective = runtime_latency + network_latency + orchestration_overhead + cost_per_token claim scope includes: region + accelerator + image + model bucket + client location
object changedThe deployment surface and accelerator/runtime boundary.
why it worksA managed or accelerator-specific path can improve utilization and operations when the workload matches the serving assumptions.
failure boundaryCloud setup, auth, bucket layout, network path, and autoscaling policy become part of the measured system.
lab proofJetStream is a second-order followup until the same-host TGI/vLLM capstone proof returns.
adaptation math

Unsloth belongs in the inference story because behavior changes must be separated from serving-speed claims.

LoRA

Source: LoRA and Unsloth SFT notebooks.
full update: W' = W + Delta W LoRA update: Delta W = B A rank(Delta W) <= r trainable_params ~= r * (input_dim + output_dim)
object changedThe trainable update space. The base model is frozen; the adapter learns a low-rank correction.
why it worksMany task changes do not need a full-rank movement through parameter space. A low-rank direction can steer behavior with far fewer trainable weights.
failure boundaryIf the needed change is not well represented at rank r, adapter training can plateau or overfit.
lab proofOur Unsloth SFT runs prove setup, adapter archive creation, hashing, reload, and bounded behavior change.

GRPO-style reward learning

Sources: Unsloth GRPO notebooks and local reward-contract probes.
sample a group of outputs for one prompt: y_1...y_g score each output: r_i = reward(y_i) relative advantage: A_i = (r_i - mean(r_group)) / std(r_group) update increases probability of above-group outputs while constraining drift from the reference policy
object changedThe probability assigned to sampled behaviors, guided by relative rewards inside a group.
why it worksThe baseline is the group itself. That reduces dependence on a separate critic and turns reward differences into directional pressure.
failure boundaryA bad reward function teaches the wrong thing precisely. Tiny runs prove the plumbing, not general reasoning quality.
lab proofOur GRPO mini-runs prove reward-contract shape and training workflow; held-out quality remains locked because the measured delta is zero.
evidence math

The capstone is a proof discipline: one mechanism, one claim, one boundary.

The mathematical through-line is that optimization claims are conditional. A method works when it relaxes the active constraint for the workload. It fails or becomes irrelevant when another term is binding.

claim unlock rule: if mechanism changes term T and workload is bottlenecked by T and experiment holds other terms fixed and metric moves in the predicted direction then publish a bounded claim else publish a diagnostic or keep the claim locked
HF and Colab evidenceGood for proving loading, tokenization, cache behavior, quantization fit, speculative acceptance, and adapter workflow.
Locked host evidenceTGI/vLLM production winner stays locked until both runtimes return same-workload host measurements.
