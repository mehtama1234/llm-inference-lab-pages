capstone readiness checklist

The serving recommendation is locked until every gate has direct evidence.

This page is the audit checklist for the capstone. It says which calculations, Colab runs, Unsloth artifacts, and matched host replay results are required before the case file can move from draft to defended recommendation.

current stance

The capstone is structurally ready, but the production recommendation is not unlocked.

The public writeups now define the mathematical frame, source map, proof sketches, experiment design, and draft case file. The remaining question is evidence: the final recommendation needs a matched host replay and clear pass/fail thresholds.

readiness gates

Each gate unlocks one claim and only one claim.

Workload gate required evidence
Frozen request JSONL with IDs, prompt template, retrieved context policy, output cap, and tokenizer. pass condition
Token distribution is measured and matches the case-file assumptions or the assumptions are updated. fail condition
Prompt shape changes during benchmark, or token counts are inferred instead of measured. unlocks
Workload-specific token and context claim.
Memory gate required evidence
Model config, dtype/quantization, KV heads, head dim, layer count, memory logs, and OOM/rejection boundary. pass condition
Weight + KV + runtime overhead estimate explains observed fit or rejection behavior. fail condition
VRAM numbers are missing, or observed admission contradicts the byte estimate without explanation. unlocks
Capacity and headroom claim.
Colab/HF gate required evidence
Notebook or CLI logs for tokenization, model load, cache/quant/speculative probes, package versions, and GPU metadata. pass condition
Each mechanism moves the predicted metric or records a bounded failure. fail condition
Only screenshots or informal notes exist; no reproducible artifact or result JSON exists. unlocks
Mechanism and workflow claim.
Unsloth gate required evidence
Adapter manifest, training config, saved files, hashes, reload probe, and held-out prompt outputs if quality is discussed. pass condition
Adapter can be trained, saved, hashed, reloaded, and its claim boundary is explicit. fail condition
Training ran but adapter files, hashes, or reload behavior are absent. unlocks
Adapter artifact claim, not broad quality claim.
Host replay gate required evidence
Same request file, model, tokenizer, output cap, GPU, Docker boundary, client, metrics, and run logs for each runtime. pass condition
TTFT, ITL, throughput, rejection, queue depth, and GPU/KV signals are comparable across runtimes. fail condition
Any runtime uses a different model, prompt template, request order, client, or metric definition. unlocks
Runtime recommendation for this workload and host.
Non-claim gate required evidence
Final writeup contains explicit non-claims next to the recommendation. pass condition
The reader can see what was not tested without reading hidden notes. fail condition
The recommendation sounds broader than the replay boundary. unlocks
Public publication of the final case file.
promotion rule

Evidence moves through levels; it cannot skip levels.

claim levels: L0 design assumption L1 first-principles calculation L2 reproducible mechanism run L3 artifact/workflow proof L4 matched host benchmark L5 bounded serving recommendation promotion rule: L(n+1) requires direct evidence for that level, not confidence from L(n)
ExampleA KV byte formula can explain capacity pressure, but cannot prove vLLM wins.
ExampleAn Unsloth adapter hash proves artifact reproducibility, but not support-answer quality.
ExampleA Colab speed observation can motivate a host run, but cannot replace it.
failure handling

A failed gate is still useful if it locks a claim.

The lab should keep failed or incomplete runs when they clarify a boundary. A failure is bad only when it is ambiguous: no artifact, no changed variable, no constants, and no claim boundary.

failure report = gate attempted + command or notebook + artifact captured + observed failure + claim locked + smallest next isolation run
OOMPromote to a memory-boundary result if model, dtype, prompt length, and memory logs are captured.
TimeoutPromote to a latency-boundary result if queue depth, TTFT/ITL, and client behavior are captured.
Bad adapterPromote to a reward/data boundary if hashes, reload output, and held-out prompts are preserved.
