ordered ladder

Each followup should answer one question created by the baseline.

0. Baseline must happen first Run matched TGI/vLLM on the same host, model, tokenizer, workload, client, and campaign ID. Unlocks the real bottleneck: TTFT, ITL, throughput, p95, errors, memory, or setup. Public page: host worksheet.
1. Prompt shape post-baseline Vary chat template fields, RAG context length, and prefix reuse while holding runtime and model constant. Run if baseline says prefill or prefix-cache behavior is binding. Claim: prompt policy changes TTFT or memory pressure under this workload.
2. Quantized serving post-baseline Run lower-precision launch variants with separate quality, fit, and speed checks. Run if baseline says memory or fit limits dominate, not merely because quantization loaded in Colab. Claim: quantization changes fit or latency only inside the measured boundary.
3. Streaming policy post-baseline Compare first visible token, chunk rhythm, full completion time, and client/server timing fields. Run if baseline says user-visible streaming behavior matters more than total completion time. Claim: streaming changes perceived latency, not necessarily total compute.
4. Overload controls post-baseline Anchor admission limits, retry budgets, cancellation, rate limits, and breaker thresholds to measured capacity. Run if p95 latency, errors, or queue wait degrade near the load knee. Claim: control policy changes failure shape under measured traffic.
5. Adapter serving post-baseline Serve the LoRA adapter under the same request replay and measure latency, memory, and output quality separately. Run only if the product need requires changed behavior, not just faster serving. Claim: adapter serving cost and adapter quality are separate gates.
external lanes

TensorRT-LLM and JetStream belong after the baseline gives a payback target.

TensorRT-LLM external NVIDIA lane Measure engine/container setup, warmup, steady-state latency, throughput, and build-payback volume. Run if the baseline says repeated traffic is stable enough to amortize specialization. Non-claim: TensorRT setup success is not TensorRT speed evidence.
JetStream/GKE external cloud lane Prove project, quota, cluster, model bucket, endpoint, request replay, and cloud operational evidence. Run if the local/VM baseline is understood and the question becomes portability or managed serving. Non-claim: deployment readiness is not cloud latency proof.
Topology/multi-GPU external scaling lane Measure communication, placement, shard/pipeline behavior, and cross-device overhead. Run only if the chosen model or workload cannot fit or meet capacity on one GPU. Non-claim: single-GPU winner does not predict multi-GPU behavior.
followup rule

A followup is valid only if it names the baseline term it tries to move.

More experiments are useful only when they reduce uncertainty. If a followup does not say which baseline metric caused it, it should stay off the public decision path.

followup_allowed = baseline_returned and baseline_gate_passed_or_diagnostic_reason_known and followup_names_binding_metric and followup_changes_one_variable and non_claim_is_explicit examples: TTFT bad -> prompt shape or prefill policy ITL bad -> decode scheduling or active sequence policy memory bad -> quantization, KV policy, token caps p95/errors bad -> overload controls setup/payback question -> TensorRT-LLM cloud portability question -> JetStream/GKE
