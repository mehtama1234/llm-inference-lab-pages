mechanism derivation workbook

Derive the experiment gate from the equation before trusting the benchmark.

This workbook expands the paper mechanism atlas into step-by-step mathematical checks. Each section starts with a simple equation, derives the condition under which an optimization helps, then names the experiment evidence that would confirm or falsify the claim.

derivation pattern

A useful optimization proof has a sign test.

The goal is to turn "this technique should be faster" into an inequality. A method helps only if the term it reduces is larger than the overhead it adds, and only if that term is actually visible in the workload being measured.

optimization helps when: old_cost - new_cost > added_overhead public claim allowed when: same_workload && same_model && same_measurement_boundary && metric_moves_as_predicted
PreserveName the function, distribution, token order, or evidence boundary that must stay the same.
ReduceName the compute, bytes, queue wait, trainable parameters, or target calls that shrink.
RefuseIf the preserved object changed, or the reduced term was not binding, keep the claim locked.
scaled attention derivation

The sqrt(d) term keeps score variance from growing with head width.

Assume q_i and k_i are independent with mean 0 and variance 1. score = q dot k = sum_i q_i k_i E[score] = 0 Var(score) = sum_i Var(q_i k_i) = d scaled_score = score / sqrt(d) Var(scaled_score) = Var(score) / d = 1
Why this matters Softmax is sensitive to score gaps. If raw score spread grows with head width, the largest accidental score can dominate before learning has selected a useful attention pattern. The scaling term makes the pre-training score scale roughly stable across head dimensions, so probability mass can move by learned structure instead of dimension alone.
Experiment gate For inference, this mainly teaches what attention is computing. The lab should not claim an optimization from scaling; it should use the derivation to explain why logits and attention entropy remain numerically meaningful. Relevant pages: attention math, formula sheet.
FlashAttention derivation

FlashAttention helps when avoided memory traffic is larger than tiling overhead.

naive attention materializes: S = Q K^T P = softmax(S) O = P V rough memory traffic includes reading/writing S and P: traffic_naive ~= O(n^2) intermediate elements blocked attention keeps running softmax stats: traffic_flash ~= O(n * d) main tensor movement + tile reads helps if: memory_time(S,P traffic avoided) > tile_overhead + bookkeeping
Preserved object The output remains the same attention result, up to normal numerical tolerances. The algorithm changes how softmax is accumulated, not which tokens are allowed to attend. The trick works because softmax can be recomputed from block maxima and normalizers without storing the full probability matrix.
Failure boundary If the workload is decode-heavy with small active blocks, or the serving bottleneck is queueing, networking, or KV memory, faster attention kernels may not dominate end-to-end latency. Experiment gate: split prefill-heavy and decode-heavy runs instead of reporting one blended number.
KV cache and paging derivation

KV caching trades recomputation for a linear memory bill; paging reduces the wasted part of that bill.

KV bytes per active sequence: B_KV = layers * tokens * kv_heads * head_dim * 2 * bytes_per_element reserved contiguous policy: B_reserved = layers * reserved_tokens * kv_heads * head_dim * 2 * bytes_per_element waste = B_reserved - B_KV paged policy: B_paged ~= ceil(tokens / block_size) * block_size * per_token_KV_bytes waste_paged < waste when sequence lengths are variable or hard to predict
Why cache works Causal decoding preserves previous hidden states. For fixed weights, fixed prefix, fixed position scheme, and fixed mask, previously computed keys and values are identical to recomputation. Decode time drops by avoiding old projections; memory rises because old K/V vectors must remain addressable.
Why paging works Attention needs logical order, not contiguous physical addresses. A block table can reconstruct logical token order while physical blocks are allocated on demand. Experiment gate: vLLM pressure runs should measure active tokens, blocks, prefix reuse, admitted requests, and latency. A throughput number without active-KV evidence is incomplete.
queue and batching derivation

Batching helps throughput until queue wait or memory pressure eats the gain.

Let lambda = request arrival rate. Let mu(b) = service rate at batch size b. Let Wq be queue wait. stability condition: lambda < mu(b) simple waiting pressure grows like: Wq increases sharply as utilization rho = lambda / mu(b) approaches 1 batching helps if: service_time(1) - service_time(b)/b > added_queue_wait + memory_pressure_penalty
Why it works GPU kernels are efficient when there is enough parallel work. Continuous batching keeps decode steps from becoming tiny isolated launches. Throughput can rise because each wall-clock interval emits more tokens across active requests.
Claim boundary Higher tokens/sec is not automatically better service. If TTFT or p95 latency crosses the user target, the scheduler has optimized the wrong objective. Experiment gate: report throughput with TTFT, inter-token latency, queue wait, active batch, and rejection/error counts.
speculative decoding derivation

Speculation is faster only when accepted target tokens per verification call exceed the overhead.

baseline target cost for m tokens: C_base = m * C_target speculative process per cycle: draft proposes k tokens at cost C_draft(k) target verifies at cost C_verify(k) accepted tokens = A cost per accepted token: C_spec = (C_draft(k) + C_verify(k)) / E[A] speedup condition: C_spec < C_target equivalently: E[A] > (C_draft(k) + C_verify(k)) / C_target
Why it works The target model remains the authority. The draft model is useful only because it guesses multiple future tokens cheaply, and the target can validate them in larger chunks. The central variable is not draft speed alone. It is accepted target-equivalent tokens per target verification pass.
Failure boundary If acceptance is low, output caps are short, prompts are mostly prefill, or coordination overhead is high, speculation can be slower. Experiment gate: our HF speculative runs can claim target-call reduction and acceptance behavior, but not broad end-to-end speed without workload-specific latency evidence.
quantization derivation

Quantization helps when byte savings reduce the active bottleneck more than reconstruction error and overhead hurt.

original matrix multiply: y = W x quantized approximation: W_hat = dequantize(q(W)) y_hat = W_hat x error = y_hat - y = (W_hat - W) x quality risk grows when: logit_margin between top choices is small and ||(W_hat - W) x|| is large in the decision direction
Why it works Model weights often have redundancy. If the quantized matrix is close in the activation directions the workload uses, the final token ranking can remain stable. Memory fit improves roughly in proportion to bits per weight, and bandwidth pressure may fall if kernels exploit the compact representation.
Failure boundary Quantization is not a speed proof. Dequantization, unsupported kernels, or KV-dominated workloads can erase latency gains. Experiment gate: report load success, VRAM, output sanity, and task quality separately from runtime latency.
LoRA derivation

LoRA reduces training cost by restricting the update to a low-rank subspace.

full fine-tune: W' = W + Delta W trainable parameters = d_out * d_in LoRA: Delta W = B A B shape = d_out x r A shape = r x d_in trainable parameters = r * (d_out + d_in) compression ratio: r * (d_out + d_in) / (d_out * d_in)
Why it works If the task only needs a few directions of behavior change, then a low-rank update can move the model function enough without independently changing every weight. This shrinks optimizer state, gradient memory, checkpoint size, and Colab GPU pressure.
Claim boundary Adapter creation and reload prove workflow. They do not prove broad quality, reasoning improvement, or production serving speed. Experiment gate: Unsloth SFT evidence needs adapter archive, checksum, reload output, and held-out task probes before behavior claims broaden.
GRPO derivation

GRPO-style training turns within-prompt reward differences into policy pressure.

For one prompt, sample a group: y_1, ..., y_g ~ policy score each sample: r_i = reward(y_i) relative advantage: A_i = (r_i - mean(r_group)) / (std(r_group) + epsilon) training pressure: increase log probability of samples with A_i > 0 decrease or constrain samples with A_i < 0 keep policy near reference to avoid uncontrolled drift
Why it works The baseline is local to the prompt. That removes some prompt difficulty and asks a narrower question: which completion was better among siblings for this exact prompt? A useful reward creates variance inside the group. Without reward variance, there is no directional signal.
Failure boundary A brittle reward function teaches the reward loophole. A tiny training window can prove the loop runs, but cannot prove durable reasoning improvement. Experiment gate: our current GRPO lane can claim reward contract and mini-training workflow; held-out quality remains locked because the measured delta is zero.
