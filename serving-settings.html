Serving runtime settings

How Transformers, TGI, and vLLM settings fit together

Transformers settings control model loading and generation inside one Python process. TGI and vLLM settings control request routing, batching, cache memory, and multi-device serving around model workers.

First Sort By Runtime Layer

A setting only makes sense after you know which process reads it. A `generate()` argument changes one local model call. A TGI router flag changes request admission and batching. A vLLM engine flag changes KV cache space, scheduling, parallelism, or model execution.

clientsends prompt and output limit
routervalidates, queues, and batches requests
schedulerchooses prefill and decode work
workerruns model kernels and stores KV cache
metricsreports wait, TTFT, ITL, throughput, and preemption

Runtime Settings Map

Transformers

max_new_tokensgenerateCaps generated tokens. It changes how long the decode loop can run.
cache_implementationgenerateSelects dynamic, static, offloaded, or quantized cache behavior.
dtypeloadChanges parameter bytes and compute dtype if supported.
device_maploadPlaces modules on CPU, GPU, disk, or split devices.

TGI

max_total_tokensrouterSets per-request token budget: prompt plus generated tokens.
max_batch_prefill_tokensrouterLimits prompt tokens admitted into a prefill operation.
max_batch_total_tokensrouterSets total potential tokens inside a batch.
waiting_served_ratiorouterControls when waiting requests can interrupt running decode work for prefill.
max_waiting_tokensrouterControls how long waiting requests can be delayed before they must be considered.

vLLM

gpu_memory_utilizationcacheSets the fraction of GPU memory vLLM can use for the model executor and KV cache.
kv_cache_memory_bytescacheSets KV cache bytes directly and overrides automatic sizing from GPU utilization.
kv_cache_dtypecacheChanges dtype used to store KV cache values.
max_num_batched_tokensschedulerCaps tokens processed in one scheduler iteration.
max_num_seqsschedulerCaps active sequences per batch.
enable_prefix_cachingcacheAllows reuse of KV states for repeated prompt prefixes.
tensor_parallel_sizeplacementSplits model work across GPUs.
data_parallel_sizeplacementRuns multiple engine replicas. `max_num_seqs` applies per data-parallel rank.

Tuning rules from docs

KV pressureIncrease vLLM `gpu_memory_utilization`, decrease `max_num_seqs`, or decrease `max_num_batched_tokens`.memory
TTFT highMore prefill budget can reduce first-token wait for large prompts, if memory allows.prefill
ITL highSmaller prefill chunks can avoid slowing running decode steps.decode
GPU fullUse dtype, quantization, offload, tensor parallelism, or smaller active batch limits.fit
repeated promptsPrefix caching can reduce repeated prefill work when prompt prefixes match.cache
Do not treat all latency settings as the same. Some change first-token delay. Some change gaps between streamed tokens. Some change memory fit.
Batch controls are service controls. They decide what work reaches the model worker together.
Cache controls are memory controls. They decide what earlier token state can be reused and where it is stored.

Command Shapes

These commands are examples of where the settings belong. They are not meant to run on this CPU-only machine as written because TGI and vLLM serving normally require a supported accelerator for these workloads.

Transformers local process

model = AutoModelForCausalLM.from_pretrained( model_id, dtype=torch.float16, device_map="auto", ) out = model.generate( **inputs, max_new_tokens=128, cache_implementation="static", )

TGI router and model server

text-generation-launcher \ --model-id $MODEL \ --max-total-tokens 4096 \ --max-batch-prefill-tokens 4096 \ --max-batch-total-tokens 8192 \ --waiting-served-ratio 0.3

vLLM engine

vllm serve $MODEL \ --gpu-memory-utilization 0.92 \ --max-num-batched-tokens 8192 \ --max-num-seqs 256 \ --kv-cache-dtype auto \ --enable-prefix-caching

vLLM multi-GPU placement

vllm serve $MODEL \ --tensor-parallel-size 2 \ --data-parallel-size 4 \ --max-num-seqs 128

Run The Flag Simulator

This local script applies TGI-style token limits and vLLM-style KV cache limits to fixed requests. It does not need TGI or vLLM installed. The point is to see what the flags change before running a real server.

Command

cd /home/manishmehta/projects/nanoGPT .venv/bin/python trace_serving_flags.py

What to look for

Baseline TGI limits reject `retrieval` and `long-doc` because their total tokens are above `max_total_tokens`.
Tuned TGI limits admit longer requests, but `agent-run` waits because the batch token budget fills first.
vLLM KV cache capacity grows from 7.60 GB to 9.00 GB in the tuned case, but the toy setup still has high KV pressure.
`max_num_seqs` changes how many active sequences share the cache budget.
