workload assumption

Representative workload: streaming support answer with retrieved context.

The user asks a support question. The application builds a chat prompt with system instructions, customer issue text, retrieved documentation, and a short answer requirement. The model streams the answer back.

Prompt shapeSystem message + user question + 3 retrieved snippets + answer style constraint.
Latency budgetFirst token should feel quick; steady token stream should avoid long gaps.
Decision boundaryThis case file does not claim general chatbot, coding, agent, or long-document behavior.
assumed request distribution for design: p50 input tokens: 1,400 p95 input tokens: 3,200 output cap: 256 tokens streaming: required concurrency target: measured in host replay, not assumed as proof
first-principles accounting

The workload is mostly a prefill and KV-capacity problem before it is a runtime preference.

Long retrieved context makes the prefill phase visible. Streaming makes decode latency visible. The serving decision therefore needs both TTFT and ITL, plus memory headroom for active KV cache.

KV bytes per request = layers * active_tokens * kv_heads * head_dim * 2 * bytes_per_element example placeholder for a 32 layer, 32 KV-head, 128 head-dim, bf16-style KV model: KV bytes at p50 = 32 * (1400 + 256) * 32 * 128 * 2 * 2 = 868,220,928 bytes KV bytes at p95 = 32 * (3200 + 256) * 32 * 128 * 2 * 2 = 1,811,939,328 bytes read as design pressure, not final model truth: p50 active request ~= 0.81 GiB KV p95 active request ~= 1.69 GiB KV
Prefill pressure source
Input tokens create the first large attention pass. metric
TTFT, prefill queue time, prompt token count, chunked-prefill behavior.
Decode pressure source
Each generated token reads accumulated KV and streams to the client. metric
ITL, decode batch occupancy, emitted tokens/sec, tail gaps.
Memory pressure source
Weights and KV cache compete for GPU memory. metric
admitted requests, rejection point, OOM boundary, KV utilization.

decision rule

The chosen runtime should be the one whose tradeoff matches the bottleneck.

decision rule: if p95 TTFT fails because prefill queue is dominant: prefer runtime/settings that isolate or chunk prefill without wrecking ITL if p95 ITL fails during active decode: prefer runtime/settings with better decode occupancy and lower step time if rejection/OOM happens before latency fails: prefer memory policy: paging, quantization, shorter context, prefix reuse, or lower concurrency if both runtimes pass the SLO: choose the simpler operational path and document remaining headroom
vLLM candidateStrong if variable context and KV pressure dominate, especially with long prompts and shared prefixes.
TGI candidateStrong if it passes SLO while giving a clean HF-aligned serving path with streaming and metrics.
TensorRT-LLM candidateStrong if the deployment is stable enough to justify engine specialization on NVIDIA hardware.
explicit non-claims

The case file is only honest if its non-claims are visible.

not claimed until separately proven: - best runtime for every workload - best model quality for support answering - adapter improves held-out answer quality - GRPO improves reasoning - quantization preserves quality - Colab speed predicts production speed - one GPU result predicts multi-GPU or cloud autoscaling behavior
