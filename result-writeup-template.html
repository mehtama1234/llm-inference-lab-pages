result writeup template

Every experiment result should become the same kind of public evidence.

This template defines the section shape for future Colab, Hugging Face, Unsloth, TGI, vLLM, TensorRT-LLM, and JetStream results. It keeps each run tied to a mechanism, an artifact, an allowed claim, and an explicit non-claim.

contract

A result page is not a diary entry. It is a bounded evidence object.

The goal is for any reader to answer three questions quickly: what was changed, what was held fixed, and what claim is now allowed? If those three questions are unclear, the result is not ready for public use.

public result section = question + mechanism formula + changed variable + constants + command/notebook + artifacts and hashes + observed metric movement + allowed claim + locked claim + next gate
EvidenceUse logs, JSON, manifests, hashes, tables, and screenshots only as supporting evidence, not as the claim itself.
ClaimName the narrow statement the evidence supports under its exact model, host, runtime, and workload boundary.
Non-claimState what did not get proven in the same section, not in a hidden footnote.
section template

Use this structure for every future experiment result.

Question write
One sentence: what mechanism or serving behavior is being tested? example
Does KV cache reuse reduce decode recomputation enough to justify memory growth?
Mechanism formula write
The equation or inequality that predicts the metric movement. example
KV bytes = layers * tokens * kv_heads * head_dim * 2 * bytes.
Changed variable write
Exactly one main thing changed, or name why the run is multi-factor. example
Cache on vs cache off; fp16 vs 4-bit; TGI vs vLLM.
Constants write
Model, tokenizer, prompt template, request IDs, output cap, seed if used, host, GPU, client, and metric definitions. example
Same request JSONL and tokenizer for both runtime runs.
Artifact write
Notebook path, command, result JSON, archive, manifest, adapter hash, or host log. example
unsloth_sft_mini_results.json plus adapter manifest and SHA256.
Observed movement write
What metric moved and whether it matched the prediction. example
VRAM fell; acceptance rate was too low; TTFT rose under prefill load.
Allowed claim write
The strongest narrow claim directly supported by the artifact. example
This run proves adapter save/reload, not task quality.
Locked claim write
The tempting conclusion that remains unproven. example
This does not prove production speed or universal runtime superiority.
Next gate write
The smallest next run that would promote the claim one level. example
Run matched host replay with same request file and output cap.
lane variants

Different experiment families need different extra fields.

Colab/HF mechanism runs Add package versions, GPU metadata, notebook URL/path, install cells, and whether the result depends on session state.
Unsloth adapter runs Add base model, dataset slice, rank, target modules, training steps, adapter manifest, file hashes, reload prompt, and held-out prompts if quality is discussed.
Runtime host runs Add host GPU, Docker image, model path, request replay file, client, concurrency policy, TTFT/ITL definitions, queue metrics, and rejection policy.
review checks

A result is publishable only when it passes these checks.

publish checks: 1. changed variable is visible 2. constants are named 3. artifact path is present 4. measured movement is stated 5. allowed claim is narrower than evidence 6. locked claim is explicit 7. next gate is actionable 8. public page does not publish credentials, private tokens, archives, scripts, or raw notebooks
RejectA result that says "it worked" but has no artifact, no constants, and no locked claim.
ReviseA result where the metric moved but the mechanism explanation is missing or contradicts the formula.
PublishA result with a narrow claim, direct evidence, static HTML summary, and clear next gate.
