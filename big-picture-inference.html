big picture writeup

LLM inference is a chain of work, memory, waiting, and proof.

This page connects the papers, docs, Colab experiments, local traces, and host runbooks into one plain explanation. The point is not to collect benchmark rows. The point is to understand what changes when a model call becomes a serving system.

problem

The problem is not text generation. The problem is controlled repeated computation.

A trained model is a large set of stored numbers. A request arrives as text. The serving system must turn that text into token IDs, read vectors and weights, run many matrix operations, store attention history, choose one next token, append it, and do that again until the answer stops.

Text becomes counted work Prompt shape decides token count, context fit, prefill cost, and how much prefix cache can be reused.
Decode repeats After the prompt is processed, each new token triggers another model step. Small per-token costs become large when many users wait.
Memory is part of latency Weights, KV cache, active sequences, runtime buffers, and precision decide whether the server fits and how much batching it can tolerate.
first principles

The request path is one chain. Each optimization touches one link.

A single request has two different kinds of work. First, the server processes the full prompt. That is prefill. Then it produces output one token at a time. That is decode. The KV cache stores attention history so decode does not recompute the whole prompt each time.

The serving problem appears when many requests share the same GPU. The system must decide which prompts to admit, which tokens to batch together, how much cache to keep, when to stream partial output, and when to reject or slow traffic instead of letting every request wait.

what the sources share

The papers and docs keep pointing at the same pressure points.

The references do not all use the same words, but they describe the same system. Hugging Face explains model-level settings. vLLM and the PagedAttention paper explain serving pressure around KV memory and batching. TGI explains the production server path. NVIDIA and Google show what changes when runtime and deployment become explicit host contracts.

Hugging Face Transformers Prompt formatting, cache implementation, precision, quantized loading, and speculative decoding change the model call before we add a serving runtime.
vLLM + PagedAttention Serving many requests is a memory-management problem as much as a compute problem. KV blocks, active sequences, and batching policy affect waiting time.
Hugging Face TGI A production endpoint is a containerized server with launch flags, health, routing, metrics, logs, and a client contract.
NVIDIA TensorRT-LLM An optimized engine can be faster, but build time and operational complexity need payback. It is not automatically the right first runtime.
Google JetStream/GKE Cloud serving adds project, quota, storage, cluster, service, endpoint, and cost gates before performance rows mean anything.
Unsloth Adapter training and GRPO workflows can be learned on Colab. Tiny adapter runs prove artifact movement; they do not prove broad quality or serving speed.

approaches

Each approach is a different answer to the same pressure.

Change the request Use stable prefixes, fewer unnecessary tokens, and formats that leave room for output. This reduces prefill and improves cache reuse.
Change model execution Choose cache settings, precision, quantization, speculative decoding, and compile paths. Measure memory and latency separately.
Change the model artifact Use adapters or fine-tuning when behavior needs to change. Verify save, checksum, reload, and held-out quality before claiming improvement.
Change the serving runtime Use vLLM, TGI, TensorRT-LLM, or JetStream when routing, batching, metrics, and deployment contracts matter.
Change admission rules Limit prompt length, output length, active sequences, retries, and per-tenant traffic so overload does not turn into long waiting.
Change the claim only after proof A runtime winner needs same model, workload, host, GPU, client, run ID, logs, and result contract. Otherwise it is only partial evidence.
claim boundary

What we can say now, and what we cannot say yet.

Allowed now We can explain how prompt shape, cache choices, quantization, speculative decoding, vLLM queue pressure, streaming, prefix cache, and Unsloth adapter movement affect the inference path. These claims are backed by local traces, Colab GPU results, verifiers, and provenance labels.
Still locked We cannot name a production TGI versus vLLM winner. The final speed claim remains locked until both runtimes run the same workload on the same NVIDIA Docker host and the returned archive passes the fair-comparison contract.
Colab boundary.

Colab was useful for Hugging Face, vLLM probes, and Unsloth adapter learning. It is not the right surface for the current final proof because the proof depends on Docker GPU access, host identity, logs, shared workload hashes, and returned runtime files. This is not another isolated Colab benchmark.
