math first principles

LLM inference works because every word becomes a sequence of vector operations under hard memory limits.

This page connects the papers, Hugging Face notebooks, Unsloth runs, vLLM/TGI serving work, NVIDIA optimization notes, and Google serving path into one mathematical story. The aim is to explain why each method works, what it changes, and what it cannot prove by itself.

big problem

The real problem is not making a model answer. It is making repeated conditional probability cheap enough to serve.

A language model is a function that turns a token history into scores for the next token. In symbols, it estimates P(next token | prior tokens). In production, the same function is called again and again while many requests compete for the same GPU memory and compute.

request text -> token ids x_1 ... x_n model step -> logits z over vocabulary probabilities p_i = exp(z_i) / sum_j exp(z_j) sample or choose token x_(n+1) append token and repeat
Mathematical unit The unit is not a word. It is a token position with vectors flowing through layers.
Systems unit The unit is not one request. It is prompt tokens, active decode tokens, KV cache blocks, and queue slots.
Proof unit A benchmark claim only means something when model, workload, host, client, runtime, and run ID match.
core math

The transformer turns lookup, similarity, weighted averages, and matrix products into next-token probabilities.

Tokens and embeddings Tokenization maps text to integers. An embedding table maps each integer to a vector. h_0[t] = E[x_t]. This is a table lookup, but after lookup every token is a point in a learned coordinate system.
Dot products A dot product adds coordinate-by-coordinate agreements. Large positive terms pull the score up; negative terms push it down. a . b = sum_i a_i b_i. This is why matrix multiply is the workhorse: it is many dot products at once.
Attention scores Each token creates a query, key, and value. The query asks what it needs; keys describe what each position offers; values carry content to mix. Q = H W_Q, K = H W_K, V = H W_V, S = Q K^T / sqrt(d).
Causal mask During generation, position t can read positions up to t, but not future positions. The mask sets illegal future scores to a very negative number before softmax, so their probability becomes nearly zero.
Softmax Softmax turns arbitrary scores into positive shares that sum to one. softmax(s_i) = exp(s_i - max(s)) / sum_j exp(s_j - max(s)). Subtracting the max keeps the arithmetic stable.
Value mix Attention output is a weighted average of value vectors, one vector per position. O = softmax(S) V. The model is literally blending earlier token states according to learned relevance scores.
MLP block Attention moves information across positions. The feed-forward network transforms each position's vector independently. MLP(h) = W_2 activation(W_1 h). The expansion layer gives the model room to compute features, then project them back.
Final logits The last hidden vector is projected against vocabulary vectors to score possible next tokens. z = h_last W_vocab^T. Temperature and top-k/top-p reshape the distribution before selection.
serving math

Inference optimization works by changing which arithmetic is repeated, stored, batched, or skipped.

Prefill Prompt length n creates many token positions at once. Attention score work contains an n by n shape inside each layer, so long prompts delay the first token.
Decode After prefill, each step adds one query token but reads the stored past. The visible sequence grows by one token per step.
KV cache Instead of recomputing old K and V rows, the server stores them and reads them during decode.
KV bytes = layers * 2(K and V) * positions * KV_heads * head_dim * active_sequences * bytes_per_number

This formula explains why "the model fits" is not enough. Weights are mostly fixed after loading. KV cache grows with active traffic. Longer prompts, longer outputs, more users, and higher precision all push the same memory wall.

Continuous batching Each decode round can serve many active requests, usually one new token per active request. It works when the GPU would otherwise sit underused. It fails when admission exceeds KV memory or batch-token limits.
PagedAttention Same attention equation, different storage policy for K and V. Logical token order maps to fixed physical blocks, reducing wasted cache space from uneven request lengths.
Prefix cache If two requests share an exact token prefix, the server can reuse completed K/V blocks for that prefix. This skips repeated prefill work only when token IDs, template, and prefix boundary match.
Quantization Store weights or cache values with fewer bytes per number. It helps fit and bandwidth. It may add conversion overhead or numerical error, so speed is measured, not assumed.
Speculative decoding A smaller draft model proposes several tokens; the target model verifies them. Expected win depends on accepted draft tokens minus draft overhead. If acceptance is low, the extra work can erase the gain.
Queue control If arrivals are faster than service, waiting grows without bound. Rate limits, admission caps, timeouts, and retry budgets are mathematical controls around finite service rate.
per paper and source

Each source is teaching one part of the same chain.

vLLM PagedAttention paper The paper's central move is not changing attention math. It changes KV cache allocation. Attention still reads K and V in token order, but physical memory is split into blocks. This lets the runtime admit more uneven-length sequences before memory waste becomes the bottleneck. Source: arxiv.org/abs/2309.06180.
vLLM blog The blog makes the systems intuition concrete: requests grow and finish at different times, so contiguous reservation is a bad fit for dynamic KV memory. Block tables preserve logical order while allowing physical reuse. Source: vllm.ai/blog/2023-06-20-vllm.
Hugging Face Transformers The model-level docs explain knobs close to model.generate(): cache choice, precision loading, quantization, static cache, compilation, and speculative decoding. These affect memory, repeated decode work, or launch overhead before we even add a serving runtime. Source: Transformers LLM optimization docs.
Hugging Face TGI TGI turns generation math into a service with router, launcher, model server, queues, streaming, token limits, batching controls, metrics, tensor parallelism, quantization, and attention kernels. Source: TGI docs.
NVIDIA inference optimization NVIDIA's material focuses on making the same graph run faster: precision, KV cache, batching, kernel efficiency, and engine optimization. TensorRT-LLM can pay off when repeated production traffic justifies build and deployment complexity. Source: NVIDIA inference optimization.
Google JetStream/GKE Google adds the cloud deployment proof: model storage, project identity, quota, cluster, service endpoint, and operational readiness. It is not new token math; it is the proof that the serving system can exist on managed infrastructure. Source: JetStream on GKE tutorial.
Unsloth notebooks Unsloth is the training-adapter lane. LoRA changes a weight matrix from W to W + A B with low-rank trainable factors. GRPO-style runs create reward-shaped updates from grouped completions. Our tiny Colab runs prove setup, adapter creation, reload, and contract boundaries, not general quality. Source: Unsloth notebooks.
what we ran

Our experiments separate mechanism proof from speed proof.

Hugging Face / Colab Tokenizer, chat-template, cache, quantization-fit, and speculative-decoding probes show how model-level settings change token count, memory, and decode work.
vLLM / Colab Serving probes show queue pressure, active sequences, prompt and output length pressure, prefix cache behavior, and streaming latency shape.
Unsloth / Colab Setup, SFT LoRA, reload, GRPO reward contract, GRPO mini-run, reload, and quality probe show that adapter workflows run and produce bounded artifacts.
Not yet unlocked The final TGI versus vLLM speed claim is locked until the same workload runs on the same NVIDIA Docker host and returns the archive.
Why this matters Colab is good for learning mechanisms. A fair runtime comparison needs controlled host, GPU, model, workload, and client conditions.
Next after host proof Prompt-shape pressure, quantized serving variant, TensorRT-LLM build payback, JetStream cloud gate, and overload controls anchored to measured capacity.
meaty end-to-end goal

The capstone is a defended serving decision, not a pile of notebook outputs.

The strong end-to-end goal is to take one workload from text shape to production serving choice. We should be able to say: here is the prompt and output distribution, here is how many tokens it creates, here is the prefill/decode split, here is the KV memory bill, here is what model-level settings changed, here is what vLLM and TGI did on the same host, here is the overload policy, and here is the narrow claim we can defend.

defensible claim = same model + same workload + same host + same GPU + same client + same run id + measured TTFT, ITL, throughput, p95 latency, queue wait, GPU memory, and logs
Boundary

Math explains why an optimization should help. Experiments decide whether it helped here. Public pages should keep those two things separate: mechanism, measured result, claim boundary, next proof.
