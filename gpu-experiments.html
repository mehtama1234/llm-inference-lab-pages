First-Principles Reading Path

The problem we are solving is direct: make a model produce the next token fast enough, keep the needed past state in GPU memory, and do it for more than one request when possible. Every experiment below changes one part of that problem.

1. Matmul Size And Precision

Matrix multiply is the repeated arithmetic inside projections and output scoring. The rows compare shape, precision, time, and measured trillion operations per second.

A model layer stores numbers called weights. The current token state is multiplied by those weights to produce new numbers for the next part of the layer.
A larger matrix gives the GPU more same-shaped arithmetic in one step. Small work can leave GPU units waiting; large work can keep more of them busy.
Precision means how many bytes are used for each number. FP32 uses 4 bytes. FP16 and BF16 use 2 bytes. Fewer bytes can move faster and use less memory, but carry less numeric detail.

2. Attention Prefill Versus Decode

Prefill has many query rows. Cached decode has one query row, but it still reads cached keys and values for the earlier positions.

Attention asks which earlier positions should affect the current position. It does this by scoring query rows against key rows.
Prefill handles the whole prompt. Many positions need scores, so the score table is large.
Cached decode handles one new token. It has one new query row and reads stored key/value rows from earlier tokens.

3. KV Cache Bytes

KV memory is stored tensor data. It grows with layers, K/V tensors, positions, heads, head dimension, batch, and bytes per stored number.

Without a cache, each new token would force repeated work over earlier tokens. The cache stores the key and value rows produced by earlier steps.
The cost is GPU memory. Longer context means more positions stored. More active requests means more cache stored.
This is why context length is not only a text limit. It is also a memory limit.

4. Decode Batch Scaling

Batch size changes how many decode tokens share one GPU step. Higher batch can raise tokens per second while each step may take longer.

One request at a time can waste available GPU work capacity during decode because each request adds only one new token per step.
Batching puts several requests into the same decode step. The GPU does more useful work before control returns to the CPU.
The tradeoff is waiting and memory. A server may hold a request briefly so it can join a batch, and each request brings its own KV cache.
