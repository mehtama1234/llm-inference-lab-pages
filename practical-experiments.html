learning loop

The rule for every experiment.

1. PredictSay what should change before looking at numbers. Example: longer prompt should raise first-token delay.
2. RunRun one controlled experiment. Change one variable at a time: prompt length, output length, batch, cache, dtype.
3. ExplainUpdate the diagram and write what moved: time, memory, waiting, fit, or output quality.

completed experiment 01

        
Cached vs no-cache decode result.

        

          This run uses a plain PyTorch attention block on an NVIDIA L4. It is a
          focused mechanism test, not a full serving benchmark.
        

        

          
what we changedNo-cache rebuilds Q/K/V rows for the full growing sequence. Cached decode projects one new token and reads stored K/V rows.

          
what proved trueThe repeated input-token work grows sharply without cache. At 4096 prompt tokens, cached decode became faster in this run.

          
what surprised usFor small prompts, cached was slower in this synthetic loop. Small one-token GPU steps can be dominated by overhead and less favorable shapes.

completed experiment 02

        
Prompt length vs first-token work.

        

          This run measures a transformer-like prefill block on an NVIDIA L4.
          It shows why long prompts mainly hurt the wait before the first token.
        

        

          
what we changedPrompt length increased while the block shape stayed the same.

          
what proved trueScore cells grew with prompt length squared, and prefill time jumped sharply at larger prompts.

          
what to noticeSmall prompt timings are dominated by launch and shape effects. Large prompts reveal the scale problem clearly.

completed experiment 03

        
Output length vs decode cost.

        

          This run keeps the prompt fixed at 1024 tokens and changes the answer
          length. It shows why long answers cost repeated decode steps after
          streaming begins.
        

        

          
what we changedOutput tokens increased from 16 to 1024 while prompt length stayed fixed.

          
what proved trueTotal decode time grew almost linearly because every output token runs another cached decode step.

          
what to noticeMilliseconds per token stayed nearly flat in this focused run, so answer length mainly multiplies the same step.

completed experiment 05

        
Fixed KV reservation vs paged KV blocks.

        

          This local simulation compares reserving the maximum token room for
          every request against allocating small KV blocks close to actual use.
        

        

          
what we changedSame request mix, two allocation rules: fixed max reservation and 128-token paged blocks.

          
what proved truePaged blocks kept reserved memory close to actual used token slots.

          
what to noticePaged KV is about fit and waste first. It helps throughput because more useful requests can fit.

Hugging Face model: cache on vs no cache.

        

          This run uses an actual Transformers model on the L4 GPU. It connects
          the synthetic cache mechanism to real Hugging Face code.
        

        

          
what we ranQwen2.5-0.5B-Instruct, greedy decode, 32 new tokens, cache on versus full growing sequence with cache off.

          
what proved trueFor longer prompts, cached decode became faster and kept each decode step to one new input token.

          
what to noticeFor short prompts, total cached time included prefill/setup cost, so cache was not automatically faster end to end.

Hugging Face model: batch size vs shared decode work.

        

          This run keeps prompt length and output length fixed, then sends more
          prompts through the same cached decode path at once.
        

        

          
what we ranQwen2.5-0.5B-Instruct, 256-token prompts, 64 output tokens per request, batch size 1 to 32.

          
what proved trueAggregate tokens/sec rose almost with batch size because each decode step returned one token for each active request.

          
what to noticeOne request did not stream much faster. Batching mostly helps the GPU serve more requests at once, while memory and first-token work rise.
