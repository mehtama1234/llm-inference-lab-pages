adapter training math

Adapter training changes behavior by adding a small learned update to a frozen model.

This page explains why LoRA, QLoRA, and Unsloth-style notebook runs belong in the inference lab. They do not optimize serving directly. They answer a different question: can we change the model's behavior with a small portable artifact while keeping the base model fixed?

problem

Full fine-tuning is expensive because every weight becomes trainable state.

A pretrained model is a function with many matrices. Full fine-tuning changes those matrices directly. That means gradients, optimizer states, and updated weights for a very large parameter set. Adapter training asks whether the needed behavior change can be represented by a much smaller update.

base inference: y = f(x; W) full fine-tune: y = f(x; W + DeltaW_full), where every element of W may move adapter fine-tune: y = f(x; W + DeltaW_small), where DeltaW_small has constrained form
Serving question How cheaply can fixed weights answer many requests?
Adapter question How cheaply can we move model behavior for a task or style?
Quality question Did that movement generalize beyond the tiny training probe?
low-rank update

LoRA restricts the weight update to a product of two small matrices.

A dense matrix update can change every direction independently. LoRA assumes the useful change lives in a lower-dimensional subspace. Instead of learning a full update matrix, it learns two thinner matrices whose product has rank at most r.

original layer: y = x W LoRA layer: y = x (W + (alpha / r) A B) W is frozen A and B are trainable rank(A B) <= r
Why it can work Many task adaptations do not need an arbitrary full-rank move in weight space. If the useful change lies near a few directions, low rank captures enough movement at much lower cost.
Parameter count Full update: d_in * d_out trainable values. LoRA update: r * (d_in + d_out) trainable values for that matrix.
Inference boundary The adapter can be merged into weights or applied at runtime depending on tooling. Adapter creation is not the same as proving TGI/vLLM serving speed.
quantized base

QLoRA freezes a quantized base and trains adapters through it.

QLoRA lowers memory by keeping the pretrained base model in a low-bit quantized form while training LoRA adapters. The gradients update the adapter parameters, not the base quantized weights.

base weights: W_quantized = quantize(W) forward path: y = f(x; dequantize(W_quantized) + A B) training: update A, B keep W_quantized frozen
Memory win Frozen base weights take fewer bytes, and optimizer state is needed mainly for adapter parameters.
Approximation risk The quantized base approximates the original base. Training must still produce useful logits through that approximation.
Claim boundary A QLoRA setup proof says the path fits and runs, not that the resulting model is generally better.
supervised fine-tuning

SFT moves the adapter by penalizing wrong next-token probabilities on examples.

In supervised fine-tuning, each training example gives target tokens. The model assigns probabilities to those tokens. The loss is high when the target tokens receive low probability. Gradient descent changes adapter weights to lower that loss.

for target sequence y_1 ... y_T: loss = - sum_t log P_adapter(y_t | prompt, y_1 ... y_(t-1)) update: A <- A - learning_rate * gradient_A(loss) B <- B - learning_rate * gradient_B(loss)
What SFT learns It increases probability of target continuations under the training distribution. It does not automatically prove reasoning, safety, or broad task quality.
Why held-out probes matter The model can memorize tiny examples or learn formatting cues. A separate held-out set checks whether the behavior moved beyond the exact training rows.
group reward optimization

GRPO-style training uses relative rewards across sampled completions.

Reward optimization does not start from one gold token sequence in the same way as SFT. It samples completions, scores them, and updates the policy toward completions that scored better under the reward rule.

for one prompt: sample completions c_1 ... c_G score rewards r_1 ... r_G advantage_i = normalize(r_i within the group) update adapter to raise probability of completions with positive advantage and lower relative probability of poor completions
Why it can work The reward gives a direction when exact target text is not the only acceptable answer.
Reward risk The model optimizes the reward it sees. A narrow reward can teach shortcuts.
Tiny-run boundary A two-step GRPO run is an API and artifact proof. It is not evidence of stable reasoning improvement.
Unsloth lane

Unsloth is useful here because it makes adapter experiments cheap enough to run in Colab.

The Unsloth notebook path gives us a practical way to run setup, SFT, GRPO reward-contract checks, adapter save/reload, and held-out probes on a rented notebook GPU. In this lab, its role is learning-by-doing for adapter workflows, not replacing the serving runtime proof.

Setup proof Install/import path, GPU metadata, package versions, and a successful model/adaptation path. This proves the notebook environment can run the workflow.
Artifact proof Saved LoRA adapter files, tokenizer/config files, archive hash, manifest, and fresh-session reload. This proves the training output is portable enough to inspect and reuse.
Quality proof Requires longer training, held-out prompts, baseline comparison, reward audit, and repeated runs. Our tiny Colab runs intentionally do not claim this.
sources and claim boundary

The adapter lane changes model behavior; the serving lane measures runtime behavior.

LoRA paper LoRA freezes pretrained weights and learns low-rank trainable matrices inside transformer layers. Our page uses that as the mathematical reason adapter files can be much smaller than full model updates.
QLoRA paper QLoRA backpropagates through a frozen quantized base into LoRA adapters, lowering memory enough for larger fine-tunes. Our Colab setup lane should be read as a memory/workflow proof before any quality claim.
PEFT and Unsloth Hugging Face PEFT LoRA docs and Unsloth notebooks are the practical notebook/tooling bridge. They tell us how to run the workflow; our artifacts tell us what we actually ran.
Final boundary Adapter result: did behavior move under a training/evaluation protocol? Serving result: did TGI or vLLM serve the same workload better on the same host?
